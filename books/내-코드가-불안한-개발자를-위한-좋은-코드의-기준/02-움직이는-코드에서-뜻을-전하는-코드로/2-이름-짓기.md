# 이름 짓기

> [움직이는 코드에서 뜻을 전하는 코드로](./README.md)

## 빠른 복습
- 이름은 **각각의 요소를 단적으로 나타내야 한다.** **이름으로 내용을 추측할 수 있다면 코드를 하나하나 확인하지 않아도 되고, 전체 코드는 읽기 쉬워진다.**
- **짧은 이름보다는 뜻이 있는 이름이 낫다.** `flag` → `isCompleted`.
- **"뜻이 한정되지 않은 단어"는 지양한다.** `checkUserStatus` 는 어떤 상태인지 알 수 없다.
- **행위가 주 목적인 함수는 행위를 중심으로 이름을 짓고**, 반환값의 뜻은 **주석으로 보충**한다.
- **단위를 이름에 담으면 명확해진다.** `averageTime` → `averageSecondsToComplete`. 다만 **자료형으로 알 수 있는 정보는 생략**해도 된다 — `Duration` 이면 `averageToComplete`.
- **문맥상 분명한 단어는 삭제한다.** `TodoReport` 안에서 `Todo` 를 반복할 필요가 없다.
- **일반적으로 함수는 동사로 시작하고 속성은 명사구로 표현**한다. **가급적 영어 문법을 따른다** — `getCompleteTask` 보다 `getCompletedTasks`.
- **같은 것에는 같은 이름**을 쓰고, **단일 문맥 안에서 서로 다른 것에는 서로 다른 이름**을 쓴다. 그래서 **주요 용어는 미리 정해두는 게 좋다.**
- **이름이 지나치게 길어지거나 필요한 정보를 충분히 담을 수 없다면, 코드 설계나 분할 방법에 문제가 있을 가능성**이 있다.

## 뜻이 있는 이름

- **각각의 요소를 단적으로 나타내야 한다.**
- **이름으로 내용을 추측할 수 있다면 코드를 하나하나 확인하지 않아도 되고 전체 코드는 읽기 쉬워진다.**
- **정확하지 않고 애매한 이름을 쓰면 혼란스럽다.**
- **짧은 이름보다는 뜻이 있는 이름이 낫다.**

```kotlin
// 개선 전
class TodoTask(val title: String, val flag: Boolean)

// 개선 후
class TodoTask(val title: String, val isCompleted: Boolean)
```

> **이름에 충분한 정보를 담으면 코드를 자세히 분석하거나 애매하게 추측하지 않아도 의도를 쉽게 이해할 수 있고, 확장성도 좋아진다.** 삭제했는지 여부는 `isDeleted` 등으로 나타낼 수 있다.

**확장성이 함께 좋아진다는 대목**을 눈여겨본다. `flag` 하나로 버티던 클래스에 두 번째 진릿값이 생기면 `flag2` 가 되지만, `isCompleted` 가 있는 클래스에는 `isDeleted` 를 자연스럽게 붙일 수 있다.

## 뜻이 한정되지 않은 단어를 피한다

```kotlin
fun checkUserStatus(user: User): Boolean { ... }
```

**어떤 상태를 나타내는지 모호하다.** 유료 회원인지를 뜻한다면 이렇게 쓴다.

```kotlin
fun isPaidUser(user: User): Boolean { ... }
```

그런데 **함수가 실제로 하는 일이 "유료 회원 여부를 로그로 보내는 것"** 이라면 이야기가 달라진다. 이때는 **로그를 보내는 동작에 주목해 이름을 짓고**, 반환값은 주석으로 설명한다.

```kotlin
/**
 * 유료 등록 회원 여부를 로그로 출력한다.
 * 로그 보내기에 성공하면 true, 실패하면 false를 반환한다.
 */
fun sendPaymentStatus(user: User): Boolean { ... }
```

> **함수 이름으로 동작과 반환값까지 설명될 수 있다면 최선이지만, 행위가 주 목적인 함수는 행위를 중심으로 이름을 지어야 한다.** 함수 이름으로 **반환값까지 억지로 설명하려 하면 이름이 길어지고 부자연스러워져 의미를 알 수 없게 된다.** 이럴 때는 주석으로 보충한다.

이 판단이 [다음 절 주석](./3-주석.md)의 존재 이유다. **이름과 주석은 경쟁 관계가 아니라 역할 분담**이다.

## 오해를 부르는 이름

완료까지 걸린 시간을 계산하는 기능에서 `averageTime` 이라고만 쓰면 **완료되지 않은 태스크의 경과 시간도 포함될 것으로 착각**할 수 있다.

```kotlin
// 오해의 여지가 있다
class TodoReport(val averageTime: Int, ...)

// 완료된 것만이라는 조건이 드러난다
class TodoReport(val completeAverageTime: Int, ...)
```

그리고 **단위**도 문제가 된다. `averageTime` 이 **일인지 초인지 알 수 없다.**

```kotlin
class TodoReport(val averageSecondsToComplete: Int, ...)
```

> **일반적으로 함수는 동사로 시작하고 속성은 명사구로 표현하는 게 바람직하다.**

## 전치사와 접속사

| 전치사·접속사 | 사용 예 | 의미 |
| --- | --- | --- |
| **to** | `moveToStart` | 시작 부분으로 이동함 |
| **from** | `createFromDefault` | 기본값을 바탕으로 생성함 |
| **for** | `observeForUpdate` | 업데이트가 있는지 확인함 |
| **until** | `waitUntilCanceled` | 취소할 때까지 기다림 |
| **by** | `searchByName` | 이름을 기준으로 검색함 |
| **and** | `nameAndEmail` | 이름과 이메일 주소 |
| **if** | `sendIfUpdated` | 업데이트했다면 전송함 |

표를 읽는 법. 전치사가 **관계를 한 단어로 압축**한다. 다만 **원칙 없이 사용하면 문제가 된다.**

- 사용자의 나이는 **`ageOfUser` 가 아니라 `userAge`** 라고 하는 게 일반적이다. 이렇게 하면 **끝 단어만 읽어도 무엇인지 쉽게 알 수 있다.**
- **여러 개의 전치사와 접속사를 사용하면 어느 단어를 수식하는지 파악하기 어렵다.**

## 너무 긴 이름

정보를 많이 담으려다 이렇게 되면 오히려 읽기 어렵다.

```kotlin
class TodoReport(val averageSecondsFromTodoTaskCreationToTodoTaskCompletion: Int, ...)
```

깎아내는 기준은 셋이다.

| 무엇을 지우는가 | 왜 지울 수 있는가 |
| --- | --- |
| **문맥상 분명한 단어** | 클래스 이름이 `TodoReport` 이므로 **TODO 앱과 관련한 보고서임은 분명**하다. 그래서 안쪽의 `Todo` 는 필요 없다 |
| **선택지가 없는 정보** | 이 앱에 시작 개념이 없다면 **'태스크를 만들고 나서(FromCreation)'** 도 지울 수 있다 |
| **자료형으로 알 수 있는 정보** | 기간을 나타내는 `Duration` 을 쓰면 **시간이라는 정보는 자료형을 보면 알 수 있다** |

표를 읽는 법. 가운데 줄에는 **반대 조건**이 붙어 있다. **이 앱에 '태스크 시작' 기능도 있어 "만들고 나서"와 "시작하고 나서" 중 언제인지 불분명하다면, 언제부터의 시간인지를 이름에 포함하는 게 좋다.** 즉 **지울 수 있는지는 코드가 아니라 도메인이 정한다.**

```kotlin
class TodoReport(val averageToComplete: Duration, ...)
```

> 초, 분 같은 시간 단위는 `Duration` 을 쓴다.

## 줄임말

```kotlin
// 한눈에 이해할 수 없다
class TodoReport(val avgToCpl: Duration, ...)
```

- **줄임말은 한눈에 이해하지 못할 것을 주의**해야 한다.
- **마음대로 만든 줄임말은 쓰지 않는다.** `TodoTask` 를 `TTask` 로 적는 식이 그렇다.
- 단 **제한된 곳에서**, 또는 **어떤 단어를 줄인 것인지 누구나 안다면** 줄여 써도 된다. `for` 문의 `i` 가 그 예다.

## 같은 것에는 같은 이름을

> `getUserName`, `getClientName`, `getCustomerName` 함수가 **실제로는 모두 같은 걸 반환한다면** 개발자는 혼란스럽고 **코드 이해와 유지보수에 어려움**을 느낀다.

- 이런 문제를 미리 막으려면 **제품에서 사용할 주요 용어를 미리 정해두는 게 좋다.**
- 또 **단일 문맥 안에서는 서로 다른 것에 서로 다른 이름**을 써야 한다.
- **문맥이 명확하다면 이름을 생략하거나 알기 쉬운 것으로 바꿔도 된다.** 사용자를 나타내는 클래스 안에서는 `userName` 보다 `name` 을 쓴다.

**주요 용어를 미리 정한다**는 이 항목이 [『아키텍트 첫걸음』 4.5의 명명 규약](../../아키텍트-첫걸음/4-아키텍처-구현/5-애플리케이션-개발-준비.md#명명-규약)과 정확히 만난다. 그 책은 명명 규약을 **구문론**(카멜 표기법 등 형식)과 **의미론**(어떤 의미의 단어를 쓸 것인지)으로 갈랐는데, **이 절의 문제는 전부 의미론 쪽**이다. 그리고 [『WMS 원리와 이해』 3.5 코드의 효율적인 설계와 운영](../../wms-원리와-이해/03-기준정보/5-코드의-효율적인-설계와-운영.md)이 기준정보 코드에 요구한 **간결성 ↔ 인식성의 균형**도 같은 문제다 — 짧게 줄이면 뜻이 사라지고, 뜻을 담으면 길어진다.

## 영어 문법을 따른다

> 앱에서 **모든 태스크 중 완료한 태스크만 가져오는 함수**를 `getCompleteTask` 로 지으면 뜻은 통하지만 **동사가 연속적으로 등장해 영어 표현으로는 자연스럽지 않다.**

- **완료한 태스크**를 나타내려면 **`CompletedTask`**(과거분사), **목록으로 반환**한다면 **`Tasks`** 로 표현하는 게 논리적이다.
- 진릿값도 주의해야 한다. **자식 태스크가 있는지 조사할 때 `is` 를 쓰면 `TodoTask is have children` 같은 표현**이 되어버린다. 여기서는 **`hasChildren`** 이 적절하다.

| 분류 | 패턴 | 예 | 설명 |
| --- | --- | --- | --- |
| **Be 동사** | `is` | `isAdmin` | 관리자인가? |
| **Be 동사** | `was` | `wasProcessed` | 이미 처리했는가? |
| **동사(3인칭 단수)** | `has` | `hasImage` | 이미지가 있는가? |
| **동사(3인칭 단수)** | `contains` | `containsKeys` | 키를 포함하는가? |
| **조동사** | `can` | `canRemove` | 삭제할 수 있는가? |
| **조동사** | `should` | `shouldUpdate` | 업데이트해야 하는가? |

**진릿값임이 분명하다면 `is` 를 생략하고 형용사나 분사만으로 표현**하기도 한다.

| 분류 | 예 | 설명 |
| --- | --- | --- |
| **형용사** | `visible` | 보이는가? |
| **형용사** | `valid` | 유효한가? |
| **현재 분사** | `playing` | 재생 중인가? |
| **현재 분사** | `loading` | 읽는 중인가? |
| **과거 분사** | `loaded` | 읽기가 끝났는가? |
| **과거 분사** | `connected` | 접속되었는가? |

표를 읽는 법. 두 표가 함께 말하는 것은 **문법이 곧 의미의 구분**이라는 점이다. `loading` 과 `loaded` 는 **분사 시제 하나로 진행과 완료를 가른다.**

## 표기법은 언어와 프레임워크를 따른다

| 표기법 | 예 | 규칙 |
| --- | --- | --- |
| **카멜 케이스** | `todoTask` | 단어 시작마다 대문자 사용 |
| **스네이크 케이스** | `todo_task` | 밑줄로 단어 연결 |
| **케밥 케이스** | `todo-task` | 하이픈으로 단어 연결 |

코틀린의 규칙은 이렇다.

- **클래스와 객체 이름은 대문자로 시작하고 카멜 케이스**로 표기한다.
- **함수, 속성, 지역 변수 이름은 소문자로 시작하고 카멜 케이스**로 표기하되 **밑줄은 사용하지 않는다.**

> 이를 따르지 않고 **맨 앞에 대소문자를 마음대로 사용하면 코드를 읽는 다른 사람이 클래스인지, 객체인지, 다른 것인지 혼동하기 쉽다.**

## 이름이 안 지어질 때

> **이름을 아무리 고민해도 이름이 지나치게 길어지거나 이름에 필요한 정보를 충분히 담을 수 없다면, 코드 설계나 분할 방법에 문제가 있을 가능성**이 있다.

이 문장이 이 절에서 가장 실용적이다. **이름 짓기의 어려움이 설계 문제의 신호**라는 뜻이며, 그때는 이름을 더 고민하는 대신 **나누는 방법을 다시 볼 일**이다(3장의 주제다). [『아키텍트 첫걸음』 2.3의 SRP](../../아키텍트-첫걸음/2-소프트웨어-설계/3-소프트웨어-설계-원칙과-실천-방법.md#srp--단일-책임-원칙)가 말한 **"이 클래스가 하는 일이 하나인가"** 를 이름으로 되묻는 셈이다.
