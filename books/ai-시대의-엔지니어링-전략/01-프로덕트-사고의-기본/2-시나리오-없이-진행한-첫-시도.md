# 시나리오 없이 진행한 첫 시도

> [프로덕트 사고의 기본](./README.md)

## 빠른 복습

- 밥Bob은 피드백을 읽고, 지표를 추적하고, 구현이 싸고 안정적인 설계를 냈다. **과정 자체는 나무랄 데가 없었다.**
- 그런데도 결과는 **활성 사용자 6%만 사용, 주문 0.3% 증가**였다.
- 원인은 **발견 단계를 건너뛰고 곧장 데이터베이스 설계로 뛰어든 것**이다.
- 그래서 리뷰에서 프로덕트 의사 결정이 아니라 **구현 쟁점이 가장 중요한 문제인 양 다뤄졌다.**
- 교훈: 좋은 실행은 잘못된 문제 정의를 구제하지 못한다.

## 밥이 한 일

밥은 모바일 앱 엔지니어인데, 업무에 사용자 시나리오를 쓰지 않는다. 앱 피드백 위젯에 올라온 사용자 의견을 훑어봤다.

- 커피 음료를 주문하는 사람들은 매번 커스터마이징을 다시 입력하는 데 지쳐 있다.
- 최근 주문 목록을 뒤지는 것도 싫어한다. 원하는 항목이 다른 메뉴와 섞인 주문 안에 파묻히는 경우가 많고, 그걸 다시 분리해내기가 번거롭다.

밥은 앱 구조에 잘 맞는 목업을 만들었다. 앱 하단에 '즐겨찾기' 메뉴 항목을 추가하고, 사용자의 즐겨찾기를 보여주는 새 페이지를 만든다. 오른쪽 위에는 새 즐겨찾기를 추가하는 `+` 버튼이 있다.

| 홈 화면 | 즐겨찾기 화면 |
| --- | --- |
| 음료 광고 | ←　　**[새 요소] 즐겨찾기 추가 ⊕** |
| **[새 요소] 즐겨찾기** · 메뉴 · 계정 · 매장 | **[새 요소] 사진 · 음료 1 · 지금 주문** |
|  | **[새 요소] 사진 · 음료 2 · 지금 주문** |
|  | 데이터는 최근 주문순으로 정렬 |
|  | **[새 요소] 즐겨찾기** · 메뉴 · 계정 · 매장 |

*원서 [그림 1-1] 밥이 제안한 모바일 앱 변경안. 새로 추가된 요소는 **[새 요소]**로 표시*

구현은 쉽다. 즐겨찾기 목록은 **기존 메뉴 위젯을 재사용**하고, '지금 주문'을 누르면 **기존 장바구니 흐름**으로 넘어간다.

새 즐겨찾기 테이블은 최근 구매순으로 정렬할 예정이라, 빠른 조회를 위해 최신 구매 시점 기준으로 인덱스를 걸어둔다.

```text
Table: favorite_items
- created_time : timestamp
- updated_time : timestamp (Index)
- item_id : long
- milk_customization: varchar
- sweetness_customization: varchar
- special_instructions: varchar
```

밥은 홈 화면의 신제품 광고 자리도 즐겨찾기로 바꾸자고 제안하지만 '신제품' 팀이 반대한다. 시즌 스페셜을 알릴 공간이 꼭 필요하다는 것이다. 밥은 마지못해 이 안을 설계에서 뺀다.

## 설계 리뷰에서 무슨 일이 있었나

대규모 검토 회의에서 다들 설계가 마음에 든다고 한다. 특히 **구현 비용이 싸다는 점**을 좋아한다.

한 사람이 이렇게 짚는다. 스타벅스 앱에는 최근 주문 목록과 장바구니에 '하트' 버튼이 있어서 항목을 바로 즐겨찾기에 넣을 수 있다고. 비슷한 버튼을 만들면 어떻겠냐는 제안이다.

밥은 반대한다. 이 버튼 하나로 **구현 시간이 두 배**가 된다는 이유다. 여러 페이지에 새 데이터베이스 쿼리를 추가해야 하는, 더 침범적인 변경이라는 것이다. 팀은 동의하고, 프로젝트는 설계대로 출시된다.

> [!WARNING]
> **리뷰의 논점이 바뀌어 있다**
> 이 회의에서 가장 까다로운 대목은 **프로덕트 의사 결정**(사용자가 즐겨찾기를 어떻게 발견하고 등록하는가)이었다. 그런데 결론을 낸 근거는 **구현 비용**이었다. 밥은 구현 쟁점이 가장 중요한 문제인 양 다뤘고, 아무도 그걸 짚어주지 않았다.

## 그저 그런 결과

몇 주 뒤 데이터를 보니 좋은 소식과 나쁜 소식이 섞여 있다.

| | 결과 |
| --- | --- |
| 좋은 소식 | 즐겨찾기 기능이 **큰 버그 없이** 출시됐다 |
| 나쁜 소식 | 활성 사용자 중 **6%만** 즐겨찾기를 쓰고, 주문은 **고작 0.3%** 늘었다 |

Tea++ 앱은 계측이 잘 되어 있어서 밥은 데이터를 파고든다. **즐겨찾기 메뉴에 들어가는 사람이 거의 없고, 들어간 사람 대부분은 곧장 나가버린다.** 저장된 즐겨찾기가 없는 사람들은 `+` 버튼을 누르기보다 그냥 떠나는 비율이 압도적이었다.

밥은 회의에서 나왔던 '하트' 버튼 아이디어를 떠올리고 카를로스Carlos를 찾아가 추가를 제안한다. 하지만 팀 우선순위는 월간 구독으로 옮겨간 상태라 당분간 만들 시간이 없다. 점포가 닫힐지도 모른다는 불안이 모두를 짓누르고 있고, 카를로스도 살짝 짜증이 난 표정이다. **밥은 자기 제품을 끝까지 마무리하지 못하게 한다는 기분으로 자리에 돌아간다.**

## 문제 원인 분석

밥은 여러 가지를 제대로 했다.

- 사용자 피드백을 들었다.
- 지표를 추적했다.
- 사용자 상호작용을 모아 살펴봤다.
- 범위를 줄여 효율적이고 달성 가능하며 안정적인 설계를 해냈다.

> [!CAUTION]
> **그런데 제안 자체가 약했다**
> 설계 리뷰에서 팀원들이 던진 질문은 흥미로웠지만 **가장 근본적인 질문은 아니었다.** 밥은 네 단계 중 첫 번째인 **발견 단계를 건너뛰고 곧장 데이터베이스 설계로 뛰어들었다.**

옆에서 문제를 짚어줄 동료가 있었다면 좋았을 텐데, 운이 따르지 않았다. 다음 절에서는 시나리오를 활용해 사용자 니즈를 고민하는 개발자를 만난다.
