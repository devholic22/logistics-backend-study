- **시나리오 형태의 프로덕트 비전에서 출발해, 이제는 전통적인 구현 요구 사항과 비슷한 형태까지** 도달했다. **시나리오 기반 발견의 방향을 따라왔기 때문에 확신을 가지고 성공을 위한 기반을 마련**할 수 있다.
- **전에 해 본 적이 없다면 SDD를 한번 시도해 보라.** **요령만 붙으면, 특히 그룹으로 하면, 이야기를 쓰는 일은 재밌고**, **제대로 된 제품을 출시하기까지 시도 횟수가 적어진다면 열 배의 배당으로 돌아올 수** 있다.

## 7.9 요약

| 얻은 것 | 이유 |
| --- | --- |
| **커뮤니케이션이 좋았다** | **누구나 이야기를 읽을 수 있기** 때문 |
| **시간을 낭비하지 않았다** | **북극성 시나리오의 요소에 집중**했기 때문 |
| **초점과 방향을 동시에** | **페르소나와 북극성 시나리오로 장기 비전을 세우되, 실행은 점진적 마일스톤 단위로만** 진행했다. **우선순위는 집중됐지만, 보다 전체적인 전략의 맥락 안에서 움직였기에 일관된 무언가를 향해 짓고 있다는 걸** 알 수 있었다 |
| **현실적인 우선순위** | **비용과 사용자 가치를 바탕으로 최상위 우선순위를 골랐고, 네 가지 잔혹한 진실을 의식**했다. **헬피는 최종 사용자에게 가치를 주기 전까지 여러 면에서 매우 강해야** 했다 |
| **출시 후 큰 재설계가 없을 전망** | **팀이 북극성 시나리오와 사용자 흐름에서 구멍을 찾았고, RFC와 사용성 조사로 사용자 흐름을 검증**했기 때문 |
| **뒤에서도 계속 쓰인다** | **설계·구현 중 시나리오 테스트를 쓸 때 유스 케이스 요약집과 사용자 흐름을 다시 참조**하고, **북극성 시나리오를 데모로도** 만든다 |

표를 읽는 법. 마지막 줄이 이 장의 산출물을 **일회용 문서가 아니라 자산**으로 만든다. 같은 이야기가 **브리프 → 요구 사항 → 흐름 → [시나리오 테스트](../04-자사-제품-체험/3-시나리오-기능-e2e-사용자-수락-테스트.md) → 데모**로 계속 재사용된다.

## 7.10~7.11 예제와 답안

**비주얼 스튜디오 코드의 확장 발견**을 소재로 한 4문항이다. **VS 코드는 린터, 문법 하이라이터, 테스트 프레임워크 같은 확장 기능을 발견할 수 있는 뛰어난 방식을 제공해 수백만 개발자의 마음을 사로잡았다.**

### 1) 북극성 시나리오

> **개발자 디애나Deanna가 한 파이썬 저장소에서 비주얼 스튜디오 코드를 켭니다.** 디애나는 **그 저장소가 처음이고 파이썬 경험도 적습니다.** 다행히 **저장소 관리자가 코드 포맷터에 대한 추천을 커밋해 둬서, 그녀에게는 설치를 제안하는 팝업이 뜨고 그걸 설치**합니다. 한편, **소스 코드 대부분이 파이썬 파일이므로 파이썬 언어 서버와 디버거에 대한 추천 확장이 제시**됩니다. **다운로드가 가장 많고 별점도 높은 것들이라, 디애나는 설치해 바로 좋은 출발**을 합니다. 마지막으로, **확장 마켓플레이스에서 쇼핑하다가 평이 좋은 AI 코딩 어시스턴트까지** 갖춰 놓습니다.

**한 이야기에 세 가지 발견 경로**가 들어 있다 — **저장소가 밀어주는 추천**, **파일 종류가 유발하는 추천**, **스스로 둘러보기**. [2장의 "여러 갈래의 길"](../02-제품-내-사용자-안내/3-발견-시나리오-온톨로지와-여러-갈래의-길.md)이 시나리오 형태로 나타난 셈이다.

### 2) 개괄적인 제품 요구 사항

- **사용자는 추천 언어 확장 리스트를 저장소에 등록하고 커밋할 수 있어서, 팀원들이 저장소를 클론할 때 빠르게 적응**하도록 도울 수 있다.
- **확장을 인기와 별점으로 정렬해 둔 라이브러리 혹은 스토어**가 있어, **어떤 언어나 저장소에 새로 들어온 사용자가 가장 효과적인 선택을 찾을 수** 있다.
- **사용자에게 추천 확장이 능동적으로 제시**되어, **확장에 대해 미리 알고 있지 않았던 신규 사용자도 빠르게 적응**한다.
- **설명, 키워드, 이름을 통해 마켓플레이스를 검색**할 수 있어 **즐겨 찾는 확장은 물론 아직 높은 순위를 차지하지 못한 코딩 어시스턴트 같은 새로운 확장**도 찾아볼 수 있다.

**"아직 높은 순위를 차지하지 못한" 확장을 명시**한 것이 좋다 — 인기 정렬만 있으면 **새 확장은 영원히 발견되지 않는다.**

### 3) 엣지 케이스 요구 사항

- **팀원이 확장을 업데이트할 때 새 추천에 대한 능동적인 안내**를 볼 수 있어야 한다.
- **사용자는 확장 설치를 거절할 수 있고, VS 코드는 사용자의 선호를 기억해 이미 거절한 확장에 대해서는 다시 안내하지 않아야** 한다.
- **저장소별 확장 혹은 전역 확장을 가질 수 있어, 코드 포맷 가이드가 다른 저장소를 동시에 쓰는 상황에 대비**할 수 있어야 한다.

**둘째 항목이 ["능동적 제안"의 그림자](../02-제품-내-사용자-안내/4-발견-시나리오-점진적-공개와-다중-페르소나.md)** 를 다룬다. 제안이 반복되면 **도움이 아니라 소음**이 되므로, 거절을 기억해야 한다.

### 4) 사용자 흐름

> 개발자 디애나가 **새 저장소를 엽니다.** **VS 코드는 그녀에게 새 저장소라는 것을 인식하고, 확장을 한번 살펴보겠냐는 팝업**을 띄웁니다. **그녀는 X로 닫거나 '확장 마켓플레이스로 가기'를 클릭**할 수 있어요. 버튼을 클릭하니, **저장소 안 언어에 맞게 필터링되고 인기와 별점의 어떤 조합으로 정렬된 추천 확장 리스트**가 나옵니다. **각 항목마다 이름, 짧은 설명, 다운로드 수, 별점, 그리고 설치install와 자세히 알아보기learn more라는 두 개의 버튼**이 보입니다. **디애나가 설치를 클릭하자, 확장 프로그램 사용법에 대한 저자가 제공한 설명과 다운로드 진행률 표시기가 표시된 페이지**가 뜹니다.

```mermaid
flowchart LR
    OPEN["새 저장소를 연다"]
    POPUP["팝업: 확장을 살펴보겠나"]

    STORE["마켓플레이스<br/>언어 필터 · 인기와 별점 정렬"]
    ITEM["이름 · 설명 · 다운로드 수 · 별점<br/>설치 / 자세히 알아보기"]
    INSTALL["설치 페이지<br/>사용법 설명 + 진행률"]

    OPEN --> POPUP
    POPUP --> CLOSE
    POPUP --> STORE
    STORE --> ITEM
    ITEM --> INSTALL

    %% lint-ok: NO-INBOUND  저장소를 여는 행동이 출발점이다
```

*사용자 흐름은 요구 사항보다 훨씬 구체적이다 — 화면에 무엇이 보이고 어떤 버튼이 있는지까지*

요구 사항("**평가가 좋은 확장을 찾을 수 있다**")과 비교하면 **흐름은 정렬 기준, 항목에 표시할 정보, 버튼 두 개까지** 정한다. 그러면서도 **"인기와 별점의 어떤 조합"** 이라고 써서 **알고리즘 세부는 설계에 남겨** 둔다 — [5절의 "설계의 여지를 남긴다"](./5-유스-케이스-요약집.md) 원칙이 흐름 단계에서도 유지된다.
