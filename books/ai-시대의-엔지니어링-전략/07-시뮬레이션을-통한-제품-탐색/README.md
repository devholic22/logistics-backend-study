# 시뮬레이션을 통한 제품 탐색

> [AI 시대의 엔지니어링 전략](../README.md)

## 아직 없는 제품의 이야기를 쓴다

> **고객 경험에서 출발해 기술로 거슬러 올라가야 합니다. 기술을 먼저 정하고 나서 어디에 팔 것인지 고민해서는 안 됩니다.**
> — 스티브 잡스

[6장](../06-타깃-오디언스-이해/README.md)에서는 **고객을 만났다.** 시나리오의 두 요소 중 **캐릭터만 다룬 셈**이다.

> 이제는 **시뮬레이션을 써 내려갈 차례**입니다. 하지만 **여러분이 만들고자 하는 이 제품, 혹은 기능은 아직 세상에 존재하지 않습니다. 그에 얽힌 이야기도 아직 어디에도 없죠.** 처음부터 제대로 만들어내고 싶다면, **우리가 사용자에게 쥐여줄 새로운 초능력을 그들이 어떻게 다뤄나갈지 예측하는 한 편의 미니 SF 소설**을 써봐야 합니다.

> 여기서부터 **프로덕트 랜드에서 시스템 랜드로 넘어가는 긴 여정**이 시작됩니다.

> [!IMPORTANT]
> **고객 경험에서 기술로 거슬러 올라가세요**
>
> 아직 없는 제품은 북극성 시나리오로 먼저 시뮬레이션하고, 그 이야기에서 요구 사항과 설계를 끌어낸다.

## 뒤늦게 터지는 요구 사항

> 소프트웨어 개발의 골칫거리 중 하나는 **뒤늦게 터지는 제품 요구 사항**입니다. **사용자 피드백에서 발견할 때도 있고, 설계와 구현을 진행하다 그제야 보이는 것들도** 있습니다. **이런 요구 사항은 프로덕트 로드맵을 늦추고 범위를 키웁니다.** **가장 큰 이유는 사전 조사 작업 부족**입니다.

원서가 제시하는 여정이다.

| 단계 | 내용 |
| --- | --- |
| ① | **프로덕트 비전을 사용자 시나리오로 마무리**한다. 이를 **북극성 시나리오**라 부른다 |
| ② | **북극성 시나리오를 잘게 나눠 유스 케이스 요약집 형태의 요구 사항**으로 만든다 |
| ③ | **로드맵을 짜되, 가장 중요한 요구 사항을 담는 첫 번째 마일스톤에 초점**을 맞춘다 |
| ④ | **첫 마일스톤에서 무엇을 만들지 제안**한다. **사용자 흐름이라는 세부 이야기를 살리고, UI가 있다면 스토리보드**도 만든다 |
| ⑤ | **선택한 각 유스 케이스에 상세 시스템 요구 사항**을 덧붙이고 **필요하면 원래 요구 사항에도 다시 반영** |
| ⑥ | **사용자 흐름과 시스템 요구 사항을 바탕으로 잡 투 비 던(JTBD) 목록**을 만든다 |

표를 읽는 법. **①→⑥이 "이야기 → 시스템"의 한 방향처럼 보이지만**, ⑤에 **"원래 요구 사항에도 다시 반영"** 이 박혀 있다. 그 되먹임이 [9절](./9-요구-사항으로의-피드백-반영.md)의 주제다.

> **어떤 프로세스도 모든 것을 보이게 해 주지는 못합니다. 사이클 후반에 놀라운 사실을 뒤늦게 알게 되는 일도 자연스럽습니다.** 다만 **그 놀라움의 크기가 훨씬 작아야 하고, 바라건대 프로덕트의 생존을 위협할 정도는 아니어야** 합니다.

## 세 개의 문서

```mermaid
flowchart LR
    BRIEF["프로덕트 브리프<br/>제품 테제 · 안티테제<br/>타깃 오디언스 · 목표 지표<br/>북극성 시나리오"]
    PRD["제품 요구 사항 문서(PRD)<br/>유스 케이스 요약집<br/>마일스톤 0"]
    SPEC["제품 명세<br/>사용자 흐름 · 시스템 요구 사항<br/>해야 할 일"]

    BRIEF --> PRD
    PRD --> SPEC
    PRD -. "피드백(요구 사항 → 비전 수정)" .-> BRIEF
    SPEC -. "피드백(설계에서 배운 것)" .-> PRD

    %% lint-ok: DEAD-END  마지막 문서가 이 프로세스의 끝이다
    classDef core fill:#93ad70,stroke:#5f7a44,color:#121a08

    class PRD,SPEC sys
```

*[그림 7-1] 프로덕트 발견 프로세스의 예시*

| 문서 | 목표 |
| --- | --- |
| **프로덕트 브리프**('프로블럼 브리프', '원 페이저') | **모두를 목표에 정렬시키는 비전 문서.** 최소한 **제품 테제와 안티테제, 타깃 오디언스(6장), 추적할 목표나 제품 지표(5장)** 를 담고 **북극성 시나리오**를 포함한다. **더블 다이아몬드 모델 관점에서 목표는 발견을 방해하는 요소를 제거**하는 것 |
| **제품 요구 사항 문서(PRD)** | **이 제품이 장기적으로 갖춰야 할 속성을 풀어내면서 첫 산출물이나 마일스톤도 제안**한다. **규범은 최소한으로.** **정의 단계의 물꼬를 트는 게** 목표 |
| **제품 명세** | **이 제품을 어떻게 설계할지** 보여 준다. **개발의 물꼬를 트는 게** 목표 |

표를 읽는 법. 세 문서가 **왜 → 무엇 → 어떻게**에 대응한다. 원서는 **특정한 프로세스를 강요하려는 것은 아니며, 만나 본 대부분의 팀도 이 세 단계를 모두 공식적인 절차로 운영하지는 않는다**고 못박는다.

## 지켜야 할 세 가지

- **작업을 여러 단계로 나눈다.** **왜·무엇·어떻게를 전부 사용자 관점으로** 보며, **각 단계에서 나중에 생각해도 될 세부 내용에 매몰되지 않도록** 조심한다.
- **각 단계에서 시나리오 시뮬레이션을 활용해 팀이 정렬을 이루고 온전한 문제를 풀게** 한다. 이것이 **시나리오 주도 발견(SDD)** 이다.
- **앞 단계로 되돌아갈 수 있는 가능성을 열어 둔다.** **이렇게 다시 반영하는 흐름이 없으면 '워터폴'** 이 된다. **워터폴은 이후 단계에서 변경하기가 어렵기 때문에 초기 단계에서 지나치게 많은 고민을 하게 만들고, 새로운 정보나 변화하는 상황에도 유연하게 대응하기 어렵다.**
