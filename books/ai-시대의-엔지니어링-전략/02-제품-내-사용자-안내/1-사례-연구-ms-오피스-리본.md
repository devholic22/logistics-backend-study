# 사례 연구 - MS 오피스 리본

> [제품 내 사용자 안내](./README.md)

## 빠른 복습
- **2000년대 중반 MS 오피스는 너무 복잡해진 탓에 사용자가 원하는 기능을 찾지도, 이해하지도 못하는** 벽에 부딪혔다.
- **2003년 MS 워드에는 도구 모음이 31개, 작업창이 19개**였다. **드롭다운 메뉴는 셈에 넣지도 않은 숫자**다.
- **사용자 수백 명을 인터뷰**해 보니 문제는 **새 기능을 찾고 익히는 일부터 막히는 것**이었다. **수요가 큰 기능은 계속 더해졌지만, 정작 쓰는 사람은 그 기능을 발견하지 못했다.**
- MS는 **오피스 2007에서 '리본' 메뉴**를 도입하고 **텍스트를 선택하면 떠오르는 맥락 메뉴**도 함께 넣었다.
- 개편하면서 팀은 **수천 개 기능의 사용 빈도 데이터를 모았고**, 그 데이터로 **새 계층형 메뉴**를 짰다.
- 결과 — **어마어마하게 복잡한 제품군이 훨씬 많은 사용자에게 닿았고, 지금까지도 검증된 설계로 자리 잡았다.**

## 기능이 늘어난 것이 문제가 아니었다

```mermaid
flowchart LR
    ADD["수요가 큰 기능을<br/>계속 추가"]
    UI["도구 모음 31개<br/>작업창 19개"]
    LOST["사용자가 기능을<br/>발견하지 못함"]
    IMP["추가한 기능의<br/>임팩트가 사라짐"]

    ADD --> UI
    UI --> LOST
    LOST --> IMP

    %% lint-ok: DEAD-END  문제가 귀결되는 지점이므로 나가는 흐름이 없다
    %% lint-ok: NO-INBOUND  기능 추가가 흐름의 출발점이다
    classDef core fill:#93ad70,stroke:#5f7a44,color:#121a08
    classDef sys fill:#e9e5a8,stroke:#a99f4d,color:#26240c
    classDef muted fill:#dcdcd2,stroke:#a8a89c,color:#3a3a30
    class LOST core
    class ADD,UI sys
    class IMP muted
```

*만든 기능과 닿은 기능 사이의 간격 — 발견에서 끊기면 나머지는 없는 것이나 마찬가지다*

> [!IMPORTANT]
> **발견은 기능의 관문이다**
>
> **"만들었다"와 "쓰인다" 사이에는 발견이라는 관문이 있다.**
>
> 기능을 더 넣을수록 관문이 좁아지므로, **기능 추가와 발견 가능성은 서로를 갉아먹는다.**

## MS가 한 일

| 조치 | 내용 |
| --- | --- |
| **리본 메뉴** | 오피스 2007에서 데스크톱 앱에 도입 — 명령을 **더 적은 수의 탭**으로 묶고 화면 영역을 넉넉히 썼다 |
| **맥락 메뉴** | **텍스트를 선택하면 마우스 옆에 떠오르는** 메뉴. 자주 쓰는 명령만 담는다 |
| **사용 빈도 데이터** | **수천 개 기능의 사용 빈도를 모아** 새 계층형 메뉴의 근거로 삼았다 |

표를 읽는 법. 세 줄이 각각 [세 국면](./README.md) 중 **발견**을 겨냥한다. 특히 셋째 줄이 중요하다 — **메뉴 구조를 취향이 아니라 데이터로 정했다.**

이 장은 이 사례를 따라가며 **여러분의 앱에서 사용자 여정을 안내할 단서**를 뽑는다. 문을 여는 소재는 **계층형 메뉴hierarchical menus**다.
