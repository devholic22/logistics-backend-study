# 발견 시나리오 - 점진적 공개와 다중 페르소나

> [제품 내 사용자 안내](./README.md)

## 빠른 복습
- **거의 모든 성공한 앱은 시간이 갈수록 기능이 늘어난다.** **단순한 검색창으로 유명한 구글조차** 이제는 탭과 도구가 여럿이다.
- 그래서 **디자이너는 복잡성을 천천히 우아하게 풀어낸다.** 이것이 **점진적 기능 공개**다.
- **리본은 기본 탭만 아홉 개**로 압도적이지만, **도형 서식 탭을 그래프 뒤쪽으로 물려 둔 우아한 드러내기** 덕에 실제 문제로 번지지 않는다.
- **앱이 복잡해지는 까닭은 하나** — **성장하면서 서로 다른 페르소나를 끌어들이고, 이들이 제각기 다른 목적으로 쓰기 때문**이다.
- **성공한 앱은 보통 두 가지 이상의 인터페이스를 함께 제공**한다. 잘 되면 **각 인터페이스가 필요한 순간에만 슬쩍 모습을 드러낸다.**
- **파워 유저는 전체의 5~20%** 정도이며, **경험을 자기 식대로 다듬을 강력한 기본 기능**을 원한다.
- 사용자가 **기능의 존재 자체를 모르는 경우**도 있다. **빵 부스러기를 흘려 두어 '모르는 것조차 몰랐던 것'을 '아는 미지known unknown'로** 바꿔 준다.

## 점진적 기능 공개

**맥락 메뉴는 필요한 순간에만 모습을 드러내는 메뉴**다. **도형 서식 탭은 도형을 누르지 않으면 화면에 나타나지 않아 UI를 어지럽히지 않는다.**

```mermaid
flowchart LR
    RIBBON["리본 탭"]
    BASE["홈 · 삽입 · 그리기 · 디자인<br/>레이아웃 · 참조 · 편지 · 검토 · 보기"]
    SHAPE["도형"]
    FMT["도형 서식 탭"]

    RIBBON -- "메뉴 훑어보기" --> BASE
    BASE -- "메뉴 훑어보기" --> SHAPE
    SHAPE --> FMT

    %% lint-ok: DEAD-END  도형을 선택해야 나타나는 탭이 종착점이다
    %% lint-ok: NO-INBOUND  리본 탭이 탐색의 출발점이다
    classDef core fill:#93ad70,stroke:#5f7a44,color:#121a08
    classDef sys fill:#e9e5a8,stroke:#a99f4d,color:#26240c
    classDef muted fill:#dcdcd2,stroke:#a8a89c,color:#3a3a30
    class FMT core
    class BASE,SHAPE sys
    class RIBBON muted
```

*[그림 2-9] 도형 서식 탭 발견을 위한 PDM — 그래프 뒤쪽으로 물려 두면 아홉 개 탭이 압도하지 않는다*

**"숨긴다"와 "뒤로 물린다"는 다르다.** 도형 서식 탭은 사라진 것이 아니라 **도형을 선택했다는 맥락 뒤에 놓여 있다.** 그 맥락에 들어온 사용자에게는 오히려 **가장 앞에** 나타난다.

워드의 또 다른 방식은 **텍스트를 선택하면 마우스 옆에 뜨는 맥락 메뉴**다. **메뉴가 알아서 자기 존재를 알리니 발견 가능성도 높고, 선택지도 많지 않아 원하는 도구를 바로 찾게** 된다.

## 다중 페르소나 설계

> [!TIP]
> **페르소나별 인터페이스를 마련한다**
>
> 성공한 앱은 보통 두 가지 이상의 인터페이스를 함께 제공한다. 잘 설계하면 **각 인터페이스가 사용자에게 필요한 순간에만 슬쩍 모습을 드러낸다.**

**MS 워드가 떠받치는 페르소나**만 해도 이렇게 넓다 — **책의 장들을 옮겨 다녀야 하는 소설가, 차트와 다이어그램이 필요한 마케터, 스크린 리더와 받아쓰기를 쓰는 시각 장애 사용자.**

**파워 유저는 전체의 5~20%** 정도로, **매우 활발하게 쓰면서 제품에 깊이 빠져 있는 사람들**이다. **경험을 자기 식대로 다듬을 강력한 기본 기능을 원하고, 제품을 속속들이 익힐 동기도 더 크다.**

| 이중 인터페이스의 예 | 두 페르소나 |
| --- | --- |
| **위키피디아 페이지의 작은 '편집' 버튼** | 일반 독자에게는 존재감이 작지만 **기여자에게는 요긴하다** |
| **큰 '가입하기' 버튼과 작은 '로그인' 버튼** | 신규 사용자 ↔ 기존 사용자 |
| **그래픽 인터페이스와 명령 셸** | 대중 ↔ IT 전문가 |
| **타입스크립트 같은 점진적 타입 언어** | 가벼운 스크립트 작성자는 **타입 주석을 선택지로**, 큰 조직은 **타입을 강제**할 수 있다 |
| **노코드·로우코드 프레임워크** | 비개발자도 다루게 하면서 **프로그래머가 커스텀 코드를 얹을 자리**를 남긴다 |
| **버튼과 키보드 단축키** | 일반 사용자 ↔ 손에 익은 파워 유저 |

표를 읽는 법. 여섯 줄 모두 **하나의 UI를 타협시켜 둘을 만족시키는 대신, 두 개의 입구를 따로 낸** 경우다. 그래서 **각 입구는 자기 페르소나에게 최적화될 자유**를 얻는다.

> 디자이너로서 얻을 수 있는 **가장 시원한 깨달음**이 하나 있습니다. **이제 여러 인터페이스를 내놔도 되는 시점이라는 사실을 알아차리는 것**입니다. 이 순간부터 **페르소나별로 따로 최적화**에 들어갈 수 있고, **설계 공간도 한층 넓어집니다.**

## 미지의 불확실성을 보이게 만들기

지금까지는 **사용자가 앱에 그 기능이 있다는 사실 정도는 안다고 전제**했다. 그런데 **존재 자체를 모른다면?** **새로 나온 혁신 기능이거나, 도메인 온톨로지를 아직 익히지 못한 신규 사용자에게 흔한 일**이다.

> **제품을 사용자가 떠도는 신비한 숲이라고 상상해 보세요. 길을 잃지 않도록 빵 부스러기를 흘려 두어야 합니다.**

MS 워드에서 커서 옆에 뜨는 **'Copilot으로 초안 작성하기' 맥락 메뉴**가 그 예다. 저자조차 그 기능의 존재를 몰랐지만, **적어도 한번 눌러 볼 수는 있게 됐다.** **모르는 것조차 몰랐던 것이 아는 미지known unknown로 바뀐 셈**이다.

### 무엇을 빼느냐도 신중해야 한다

> **사용자들은 누락된 명령어를 다른 곳에서 찾을 수 있다는 사실조차 모를 수 있습니다.**

워드는 **레이아웃 탭에서 모든 나누기 기능을 보여 주지만, 삽입 탭에는 '페이지 나누기' 명령만** 올려 둔다.

| | 효과 |
| --- | --- |
| **잃는 것** | 레이아웃 탭을 들춰 보지 않은 사용자는 **페이지 나누기가 유일한 선택이라고 오해**할 수 있다 |
| **얻는 것** | 페이지 나누기가 **애매한 '나누기' 아래에 묻혀 있을 때보다 훨씬 잘 보이게** 된다 |

표를 읽는 법. **메뉴에 무엇을 올릴지는 언제나 이 두 칸의 교환**이다. 다 보여주면 아무것도 안 보이고, 하나만 보여주면 나머지가 없는 것처럼 보인다.
