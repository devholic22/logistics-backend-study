# 예제 - foo에서 멀어지기

> [제품 내 사용자 안내](./README.md)

## 빠른 복습
- 연습의 규칙 — **무언가를 `foo`나 `bar`로 부른 뒤, 더 나은 이름을 골라 본다.**
- **`foo`는 정보가 0이니, 과제는 `foo`로부터의 거리를 최대한 벌리는 것**이다.
- **'정답'은 없지만 발견·이해·사용 시나리오를 떠올리며** 푼다.

## 문제 1 — 데이터 변경 구독

**특정 테이블의 데이터가 바뀔 때 사용자가 구독**할 수 있는 기능이다. **`DataChangeSubscription`을 서브클래싱해 등록하면 트랜잭션이 커밋될 때마다 콜백이 실행**된다.

```python
class DataChangeSubscription(ABC):
    # 구독은 특정 데이터베이스 테이블 또는 컬렉션에 적용된다.
    @abstractmethod
    def foo() -> TableType:
        ...

    @abstractmethod
    def bar(old_record, changes: Dict[str, Any]) -> None:
        ...
```

*원서 예시 — 두 추상 메서드의 이름을 무엇으로 할 것인가*

**답안**

- **`foo`는 `table_type`이면 괜찮지만, 좀 더 또렷하게는 `table_type_filter`도 고려**한다. **테이블 타입이 어떻게 쓰이는지 분명해진다.**
- **`bar`는 `on_record_changed`** 가 좋다. 이유가 세 겹이다 — **`on_` 접두사는 이벤트 핸들러에 널리 쓰는 관행**이고, **단수 `record`는 무엇이 바뀌었는지 드러내며**, **과거형 `changed`는 커밋이 이미 일어났음을 알려 준다.**
- 나중에 **변경 커밋 직전에 실행할 콜백**을 더한다면 **`on_record_changing`** 이라 부를 수 있다.
- **`DataChangeSubscription`이 데이터 변경 구독을 나타내고, 콜백은 그 변경이 완료된 시점에 실행되므로 `changed`를 골랐다.**

**시제가 정보를 나른다**는 점이 이 답안의 묘미다. `changed`와 `changing` 한 글자 차이가 **콜백이 커밋 전인지 후인지**를 말한다 — [모호성 회피](./5-이해-시나리오-이름-짓기.md)가 문법으로 실현된 예다.

## 문제 2 — 맥주 리뷰 앱

**맥주를 누르면 감상을 자유롭게 적을 수 있는 자유 텍스트 필드 `Foo`** 가 나타난다.

**답안** — **사용자 리서치를 조금 하거나 챗봇에게 물어보면, 맥주 애호가들이 맥주에 대한 묘사를 '시음 노트tasting notes'라 부른다**는 사실을 알게 된다. `description`이나 `review` 같은 일반 용어를 써도 되지만,

> **'시음 노트'라 쓰면 대상 페르소나가 '향'이나 '입안에서 느껴지는 질감'에 대해 시적 표현을 쏟아낼 가능성이 높아집니다. 우리가 바라던 풍경이죠.**

**이름이 입력의 성격까지 바꾼다.** 라벨은 설명이 아니라 **초대장**이라는 관점이며, [온톨로지를 사용자 쪽에서 가져오는 것](./3-발견-시나리오-온톨로지와-여러-갈래의-길.md)의 보상이 여기서 드러난다.

## 문제 3 — 가입 흐름 소요 시간 지표

**신규 사용자가 설문과 가입 흐름에 쓰는 시간을 추적할 집계 지표 `foo`** 를 건다.

**답안** — **팀 대시보드의 그래프를 동료들이 읽는 장면**을 떠올린다. 떠오르는 질문이 둘이다.

| 질문 | 이름에 담아야 할 것 |
| --- | --- |
| **단위가 뭐지?** 밀리초·초·분 | `seconds` |
| **어떤 지표지?** 평균·중간값·p90 | `.p50` |

그래서 **`user_signup_seconds_to_complete.p50`** 같은 이름이 나온다.

표를 읽는 법. 두 질문 모두 **그래프를 보는 사람이 이름 말고는 물어볼 데가 없는 것들**이다. 지표 이름은 **툴팁도 문서도 없이 홀로 서야 하는 자리**이므로, [중복 설명](./6-이해-시나리오-중복-설명.md)을 쓸 수 없고 이름 하나에 다 담아야 한다.

## 문제 4 — 비싼 함수

```javascript
mutual_friends = await current_user.getMutualFriends(friend_user)
```

*원서 예시 — 친구 한 명당 한 번씩 여러 명에게 동시에 호출되어 비용이 커졌다*

**알고 보니 친구 한 명당 한 번씩 여러 명에게 동시에 호출**했고, **예상치 못한 연산과 프라이버시 점검이 발생하면서 비용이 더 많이** 들었다. **당장 최적화할 시간은 없다.**

**답안** — **`getMutualFriends`가 비싼 작업이라는 점이 어떻게든 드러나야** 한다.

- **`computeMutualFriends`** 로 부르는 것만으로도 **비용을 의식하게** 만들기 충분하다.
- 나중에 이름을 바꾸기 쉽다면 **`computeMutualFriends_Expensive`** 로 **더 직설적인 것도 방법**이다.

> [!TIP]
> **못생긴 이름도 신호가 된다**
>
> 겉으로 못생긴 이름이 미래의 누군가에게 캐싱하거나 비용을 줄이려는 동기를 심어 줄 수 있다.

`get`과 `compute`의 차이가 전부다 — **`get`은 "그냥 가져온다"는 약속이고, `compute`는 "일이 벌어진다"는 경고**다. [앞 절의 `TAKE_DOWN_THE_SITE`](./7-사용-시나리오-위험을-이름에-드러내기.md)와 같은 수법을 성능 문제에 쓴 것이다.
