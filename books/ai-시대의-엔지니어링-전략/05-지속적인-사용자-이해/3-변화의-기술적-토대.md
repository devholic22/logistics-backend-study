# 변화의 기술적 토대

> [지속적인 사용자 이해](./README.md)

## 빠른 복습
- 원서는 목록을 세 묶음으로 나눈다 — **품질의 기본**, **변경을 쉽게 만드는 것**, **좀 더 고급 기법**.
- **각 컴포넌트에 그것을 신뢰할 수 있게 해 주는 메커니즘을 내장하라.** **모든 변경에는 그것이 작동하며 프로덕트 요구 사항을 만족하고, 앞으로도 그럴 것임을 보여 주는 검증이 수반**되어야 한다.
- **각 컴포넌트에 진화를 위한 메커니즘을 내장하라.** **확장 가능하고, 유지 보수가 가능하며, 중요한 의사 결정에 필요한 계측이 들어가** 있어야 한다.
- 목록의 어떤 항목은 **지금 팀에 해당하지 않을 수** 있다. **하위 호환성을 유지해야 한다거나 사용 데이터를 모을 수 있는 능력이 제각각**인 팀도 있다.
- **개발자 생산성 향상에 인력의 15~20%를 투자**하는 비율은 **개별 팀에서도 좋은 기준**이다.

> [!TIP]
> **모든 컴포넌트에 검증과 진화 수단을 넣는다**
>
> 자동화 테스트로 현재 동작을 신뢰하고, 추상화·계측·호환성 장치로 다음 변경의 비용을 낮춘다.

## ① 품질의 기본 — 신뢰를 세운다

| 항목 | 내용 |
| --- | --- |
| **자동화 테스트**(4장) | **늘 작성하되 가장 중요한 시나리오를 돌리는 쪽에 집중.** **핵심 시나리오까지 잘 담은 탄탄한 커버리지는, 변경이 가장 중요한 사용자 상호작용을 깨지 않는다는 자신감**을 준다 |
| **CI 테스트** | **새 코드가 소스 저장소에 커밋되기 전에 반드시 통과해야 하는 테스트.** **버그가 생기자마자 빠르게** 잡는다 |
| **기능 플래그** | **코드 배포와 별개로 기능을 켜고 끄는 토글.** **거의 즉시 반영되는 변경**을 가능하게 하고 **새 코드의 도입을 점진적으로 끌어올려**, **새로운 시도를 안전하게 한다는 감각**을 준다 |
| **코드 리뷰** | **모든 코드 변경이 고객 니즈를 만족하는지, 유지 보수가 가능하고 테스트가 잘 돼 있는지** 확인 |
| **운영 지표 계측** | **오류율, 흐름 완료율, 성능, 용량**을 실시간 추적하고 **어긋날 때 경보**. 특히 **나쁜 릴리스가 나갔을 때 오류를 일찍 잡을 수 있도록 보정돼 있는지** 확인 |
| **회복 탄력성 프리미티브** | **큐, 재시도, 속도 제한.** 문제가 생겼을 때 **한 시스템의 고장이 다른 시스템에 미치는 '영향 범위blast radius'** 를 줄인다 |

표를 읽는 법. 여섯 줄의 공통 주제를 원서가 직접 밝힌다 — **99.9%의 시간 동안 제대로 작동하는 시스템을 원하면서 끊임없이 업데이트도 하고 싶다면, 변경 관리 시스템이 최악의 문제를 막아 줄 거라 믿을 수 있어야** 한다. **믿음이 있어야 자주 바꿀 수 있다**는 인과다.

> **각 컴포넌트에 그것을 신뢰할 수 있게 해 주는 메커니즘을 내장하세요.**

### 테스트 문화를 심은 방법

> 오큘러스에서 제가 이룬 핵심 성과 중 하나는 **테스트 문화를 정착시킨 것**이었습니다. **페이스북의 테스트 프레임워크를 활용**할 수 있었고, **오큘러스 전용 테스트 헬퍼를 몇 가지 더해 테스트를 수월하게** 만들었어요. 그리고 **몇 달간 코드 리뷰에서 테스트를 계속 요구한 덕에, 새 문화가 성공적으로 자리** 잡았습니다.

**도구로 쉽게 만들고, 리뷰로 꾸준히 요구하는 두 축**이다. 어느 하나만으로는 되지 않는다 — 어려운 채로 요구하면 반발이 남고, 쉽게만 만들고 요구하지 않으면 안 쓴다.

## ② 변경을 쉽게 만든다

- **비즈니스 성과, 고객 수용, 고객 성공과 연결된 제품 지표를 추적**한다. **무엇을 바꿀지 결정하는 데** 도움이 된다.
- **시간이 지나며 쌓이는 하위 호환성 제약을 돌파할 도구와 프로세스에 집착**한다. **데이터베이스 마이그레이션 도구**를 만들거나, **기존 사용자를 깨뜨리지 않고 업그레이드하게 해 주는 새 API 버전을 짜는 능력** 같은 것.
- **모듈, 타입 시스템, 프로토콜 같은 추상화**를 쓰되 **버전별 하위 호환성을 염두에 두고 설계된 것**이어야 한다. **잘 추상화된 인터페이스는 팀 협업을 돕고, 관심사를 분리해 팀이 독립적으로 작업**하게 해 준다.

> **각 컴포넌트에 진화를 위한 메커니즘을 내장하세요.**

**EntSchema를 오큘러스 엔지니어에게 보여 줬던 기억**이 이어진다. **새 필드를 안전하게 코드 생성하고 데이터베이스 백필을 수행하는 일이 아주 간단**해지므로,

> 저는 이렇게 주장했습니다. **지금 PR에서 쓸데없이 미래를 예측한 필드는 걷어내도 되고 필요하면 나중에 언제든 추가할 수 있다**고 말입니다.

**"나중에 추가할 수 있다"는 사실을 증명하는 것이 과잉 설계를 없애는 방법**이다. [앞 절의 분석 마비](./2-변화를-위한-설계-오큘러스-사례.md#분석-마비)에 대한 처방이 설득이 아니라 **도구**였다는 점이 요점이다.

## ③ 고급 기법

| 기법 | 내용 |
| --- | --- |
| **잦은 배포** | **온라인 서비스라면 지속적 배포(CD)** 를 권한다. **블루/그린 또는 레인보우 배포**로 새 버전을 점진적으로 내보내고 **문제가 있을 때 즉시 롤백** |
| **베타·얼리 어답터 프로그램** | **가장 열성적인 고객이 새 기능을 테스트하고 다듬는 일을 돕고, 그들이 쓰는 부분을 깰 수 있는 릴리스를 미리 짚어** 낸다. **기능 플래그로 가능해지는 경우가 많다** |
| **점진적 롤아웃** | **무작위로 편향 없이 고른 사용자 집단에 먼저** 내놓고 100%로 끌어올린다. **매번 같은 집단이 되지 않게** — **같은 사용자가 자기도 모르게 계속 불안정한 버전을 만나면 안 된다** |
| **유연한 분석 플랫폼** | **새로운 역학이 궁금하거나 예기치 않은 문제를 좁혀야 할 때 쿼리를 쉽게 바꿀 수** 있어야 한다 |
| **A/B 테스트 프레임워크** | **서로 다른 기능 버전의 성능을 비교** |

표를 읽는 법. 셋째 줄의 단서가 실무적으로 값지다. **점진 롤아웃 대상을 고정하면 특정 사용자만 계속 베타 테스터가 된다** — 통계적으로도 편향되고, 그 사용자에게도 부당하다. [『요즘 우아한 백엔드 개발』 2장이 센터를 골라 순서를 정한 것](../../요즘-우아한-백엔드-개발/02-전체-서비스를-관통하는-도메인-모듈-안전하게-분리하기/4-Step-3-안전하게-배포하기.md#피처-플래그)과 비교하면, **의도적으로 고른 순서**와 **무작위 표본**은 목적이 다르다 — 앞은 리스크 관리, 뒤는 편향 없는 관측이다.

**오큘러스 팀을 페이스북 인프라로 옮기는 데 결정적이었던 건 스쿠바Scuba라는 유연한 분석 플랫폼**이었다. **제품 데이터를 실시간으로 자르고 썰 수 있고, 쿼리마다 인덱스를 손으로 만들 필요가 없다**는 점이 매력이었다.

## 개선 시간 확보

> **제품 요구 사항이 사방에서 쏟아지는 상황에서, 자기 기술 스택에 투자할 시간 따위는 영영 없을 것처럼 느껴지기도** 합니다.

> 앞서 기업이 **개발자 생산성 향상에 인력의 15~20%를 투자**한다고 언급했는데, **개별 팀에서도 비슷한 비율이 좋은 기준**이라고 생각합니다. **로드맵에 가장 중요한 생산성 개선 작업을 위한 시간을 확보할 수 있는지 팀과 논의**해 보십시오. 다만 **이러한 투자는 장기적으로 효과를 발휘하는 경우가 많다**는 점을 기억해야 합니다. **중요하지만 항상 긴급해 보이지 않는 일**이기도 합니다.

한편 **긍정적으로 볼 이유**도 있다 — **개발자 기술 생태계는 점점 더 정교해져 기성품 수준의 훌륭한 기술을 끌어 쓸 수** 있고, **코딩 보조 도구와 에이전트는 생산성을 높이고** 있다. **이렇게 확보한 시간을 소프트웨어 조직의 역량을 한 단계 높이는 데 활용**할 수 있다.
