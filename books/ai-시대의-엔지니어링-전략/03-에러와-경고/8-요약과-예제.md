# 요약과 예제

> [에러와 경고](./README.md)

## 빠른 복습
- 진단을 쓸 때는 **먼저 사용자 경험으로 초점을 옮긴다** — **사용자가 무엇을 알고, 무엇을 알아야 하며, 무엇을 해야 하는지.**
- 그다음 **시나리오 범주로 분류**한다. 그러면 **메타데이터와 메시지를 어떻게 구성할지 따져보기가 한결 쉬워진다.**
- 메시지에서 지킬 것 — **충분한 맥락**, **사용자 중심 온톨로지 용어**, **해결 방법 제안(답이 하나가 아니라면 대안도)**.
- **인터페이스 경계에서 에러를 던지고**, 개발자를 위해서는 **에러에 충분한 맥락과 구조**를 담는다. **에러를 위계로 정리해 두면 개발자는 일반적인 방식과 구체적인 방식을 모두 쓸 수** 있다.
- **자주 발생하거나 중요한 상황에는 시프트 레프트를 실천할 창의적인 방법**을 고민한다.

> [!IMPORTANT]
> **좋은 진단의 세 요소**
>
> - **충분한 맥락을 제공한다.** 어떤 작업을 수행하려 했는지와 문제가 된 데이터를 함께 보여준다.
> - **사용자 중심의 온톨로지에 맞는 용어**를 쓴다.
> - **해결 방법을 제안한다.** 답이 하나가 아니라면 대안도 함께 제시한다.

## 3.9~3.10 예제와 답안

### 1) 윈도우 블루스크린

**'Windows Blue Screen of Death Evolution'을 검색해 수십 년에 걸친 개선 과정을 보고, 그 메시지들이 어떤 페르소나를 겨냥하는지 판단**하는 문제다.

윈도우 11 메시지는 이렇다.

> 기기에 문제가 발생하여 다시 시작해야 합니다. 오류 정보를 수집한 뒤 자동으로 다시 시작합니다. 이 문제와 가능한 해결 방법에 대한 자세한 내용은 `https://www.windows.com/stopcode`를 방문하세요. 지원 담당자에게 연락한다면 다음 정보를 전달하세요. 중지 코드: `SOME_ERROR_CODE`.

| 무엇을 하는가 | 평가 |
| --- | --- |
| **최종 사용자를 겨냥하며 명확한 행동을 제시** | 좋다 |
| **URL을 쓴 것** | **강력한 기법.** **URL은 최신 상태로 유지할 수 있고, 세밀한 안내를 담을 수** 있다 |
| **끝부분에서 중지 코드를 언급** | **IT 전문가에게 관련된 정보임을 분명히** 드러낸다. **이 메시지에 서로 다른 두 청중이 있다는 단서** |
| 다만 **그 두 번째 청중을 돕는 데는 그리 애쓰지 않는다** | **크래시 덤프를 찾는 법 같은 건 알아서 검색할 수 있으리라 본 것** |

표를 읽는 법. **한 화면에 두 페르소나를 태운 사례**다 — [2장의 이중 인터페이스](../02-제품-내-사용자-안내/4-발견-시나리오-점진적-공개와-다중-페르소나.md)가 에러 화면에서 나타난 모습이며, **주 청중에게 자리를 주고 부 청중에게는 코드 한 줄만 남기는** 선택을 했다.

### 2)~4) 이커머스 `submit_order` 분류

**`submit_order` API는 사용자 ID, 장바구니 ID, 신용카드 CVV 코드를 받는다.** 모바일 클라이언트는 **올려보내기 전에 정적 검증을 할 수** 있다.

| 입력 | 범주 |
| --- | --- |
| **유효하지 않은 사용자 ID · 장바구니 ID** | **개발자 측 잘못된 인수.** 다만 **사용자가 로그인하지 않아 사용자 ID가 비어 있는 경우라면 사용자가 직접 처리할 수 있는 사전 조건 미충족** |
| **유효하지 않은 CVV 코드** | **사용자 측 잘못된 인수** |
| **비어 있는 CVV 코드** | **겉으로는 사용자 측 잘못된 인수.** 하지만 **잘 만든 클라이언트라면 서버에 연결하기 전에 빈 필드를 정적으로 검사**해야 하므로, **API는 이를 개발자 문제로 다루고 싶을 수** 있다 |

표를 읽는 법. 셋째 줄이 이 문제의 묘미다. **같은 입력이라도 "누가 먼저 막았어야 했는가"에 따라 범주가 옮겨간다.** **클라이언트가 정적 검증을 하기로 약속한 순간, 빈 CVV가 서버에 도착했다는 사실 자체가 클라이언트의 버그**가 된다 — **누락된 필드를 버그로 분명히 드러낼 수** 있게 되는 것이다.

### 5) CVV 누락 메시지

> 저라면 **잘못된 CVV 값을 빨간 박스로 강조**하고, 다음 설명을 담은 툴팁을 보여주겠습니다. **"신용카드의 보안 코드를 입력하세요. Visa, Mastercard, Discover 카드라면 보통 뒷면에 적힌 3자리 숫자입니다. American Express 카드는 보통 앞면에 적힌 4자리 숫자예요."**

**"어디를 보라"까지 적었다는 점**이 이 답안의 핵심이다. [4절](./4-실행-가능성-개선.md)의 표현대로 **탐색 공간을 지워 준다.**

### 6)~7) 만료된 장바구니

> **만료된 장바구니는 사전 조건 미충족이며 사용자가 직접 처리할 수** 있습니다. 따라서 **장바구니 만료를 구현할 때는 API가 유효하지 않은 ID(개발자 문제)와 만료된 ID를 구분할 수 있어야** 합니다. 예를 들어 **만료된 장바구니를 데이터베이스에서 완전히 지우지 않고 소프트 삭제soft-delete**할 수 있죠. 이 관행을 **툼스토닝tombstoning**이라 부르기도 합니다.

**데이터 모델이 에러 품질을 제한한다**는 것이 이 답의 요점이다. **행을 지워버리면 "없는 ID"와 "만료된 ID"가 같아 보이고**, 그 순간 [두 범주를 가를 근거](./2-에러-시나리오-분류.md)가 사라진다. [6절의 정보 체인](./6-프로그래밍-가능한-에러.md)이 **저장 계층까지 뻗는** 사례다.

시프트 레프트 답안은 이렇다.

> **장바구니 만료 전에 미리 이메일이나 푸시 알림으로 고객에게 주문을 마무리하라고 알려줄 수** 있습니다.

**에러를 잘 쓰는 대신 에러가 날 일을 앞당겨 없앤 것**이며, [7절](./7-조기-진단-시프트-레프트.md)이 말한 시프트 레프트의 가장 왼쪽 형태다.
