# 프로그래밍 가능한 에러

> [에러와 경고](./README.md)

## 빠른 복습
- **때로는 에러와 최종 사용자 사이에 개발자가 끼어 있다.** 그 개발자도 **인터페이스 계층에서 에러를 처리한다는 같은 원칙**을 따르며, **우리 에러를 프로그래밍 방식으로 가로채 다양한 조치를 취하려** 한다.
- **에러가 잘 설계되어 있지 않다면 이러한 처리는 불가능**하다.
- 런타임 에러(**시스템 에러, 사전 조건 미충족, 사용자 측 잘못된 인수**)를 개발자가 쓰기 쉽게 만드는 방법은 셋 — **구체적인 에러 발생**, **예외 그룹화**, **메타데이터 추가**.
- **어서션과 개발자 측 잘못된 인수는 공통 예외 타입 하나를 써도 괜찮다.** **개발 시점에 대응되므로 런타임 자동화를 이걸 중심으로 짜선 안 된다.**
- 좋은 진단은 **정보 체인**을 요구한다. **정보를 다음 단계로 넘기지 않는 첫 개발자 한 명이 체인을 끊어버린다.**

## ① 구체적인 에러를 던진다

> **`ValueError` 같은 범용 에러 타입만 사용하면, 클라이언트는 에러 종류에 따라 자동화 로직을 다르게 처리하거나 사용자에게 적절한 안내를 제공하기 어렵습니다.**

원서는 자기 예제를 스스로 지적한다. **[앞 절](./5-인터페이스에서-에러-발생.md)에서 옵저버빌리티 팀이 `ValueError`를 던진 대목이 거슬렸을지도** 모르겠다고.

> **옵저버빌리티 팀이 플랫폼 팀은 아닙니다.** 다만 **언제든 자기 컴포넌트 주변에 UI나 미들웨어가 붙을 수** 있습니다. 그래서 **습관적으로 `OncallNotFoundError` 같은 이름의 구체적인 런타임 에러를 만드는 편이 좋습니다.**

> **시스템 에러, 사전 조건 미충족, 사용자 측 잘못된 인수 같은 런타임 에러는 그 위에 코드를 얹을 수 있도록 중첩nestable을 염두에 두고 설계하세요.**

**"내 코드가 최상위일 것"이라는 가정이 오래가지 않는다**는 이야기다. 오늘의 애플리케이션이 **내일은 남의 라이브러리**가 된다.

## ② 시나리오 범주별로 묶는다

> **API 사용자는 특정 범주에서 오는 에러를 모두 처리하는 범용 핸들러를 쓰고 싶을 수** 있습니다. 예컨대 **시스템 에러가 날 때마다 "문제가 발생했습니다. 잠시 후 다시 시도해 주세요"** 를 띄우고 싶을 수 있죠. 반대로 **사용자 측 잘못된 인수 에러는 메시지를 그대로 사용자에게 전달**하는 전략을 쓸 수 있습니다.

**대부분의 언어에서는 상속 위계로 비슷한 에러를 묶을 수 있고**, 저자는 **시나리오 범주마다 별도의 기본 클래스를 두는 걸 좋아한다**고 적는다.

| 빌트인 | 한계 |
| --- | --- |
| 파이썬 **`ValueError`** — 어떤 종류든 **잘못된 인수 에러** | **사용자 측 잘못된 인수와 개발자 측 잘못된 인수를 구분하지 않는다.** **결과는 완전히 다른데도** |
| 파이썬 **`RuntimeError`** — **시스템 에러** | — |
| **HTTP 400번대** — '클라이언트' 에러 | 파이썬 `ValueError`처럼 **사용자 때문인지 개발자 때문인지 구분되지 않는다.** 다만 **인증 실패 같은 일부 사전 조건 미충족 에러에는 쓸 만한 코드**가 있다 |

표를 읽는 법. 세 줄 모두 **"클라이언트 쪽 잘못"까지만 말하고 그 안을 나누지 않는다.** 그런데 [2절의 표](./2-에러-시나리오-분류.md)가 보여준 대로 **둘은 고치는 사람도 시점도 다르다** — 원서의 표현으로는 **"프로그래머가 실수한 거라면, 사용자가 입력을 고치는 게 아니라 지원 팀에 문의해야"** 한다.

그래서 저자는 **각 범주에 클래스를 따로 만들어 `ValueError`를 서브클래싱**한다. **비객체지향 환경이라면 범주별 에러 코드와 특정 실패를 식별하는 서브코드**를 제공한다.

이 구분은 [『요즘 우아한 백엔드 개발』 24장의 커스텀 예외](../../요즘-우아한-백엔드-개발/24-illegalargumentexception은-400-bad-request인가/3-그러면-어떻게-매핑할-것인가.md)와 정확히 같은 처방이다. 그 글은 **`IllegalArgumentException`이 서버 버그와 클라이언트 입력 오류를 함께 담기 때문에 400으로 일괄 매핑하면 안 된다**고 했다. 여기서는 **`ValueError`가 같은 문제를 갖는다**고 말한다.

## ③ 진단용 정보를 유지한다 — 정보 체인

> 좋은 에러 메시지를 만들려면 **많은 정보를 계속 데리고 다녀야** 합니다. 이건 **꼼꼼함과 잘 조직된 코드**를 요구합니다. **정보를 다음 단계로 넘기지 않는 첫 개발자 한 명이 체인을 끊어버리거든요.**

### 고수준 추상화를 넘긴다

> **자잘한 정보를 이것저것 넘기지 마세요. 정보를 묶은 더 높은 수준의 추상화를 넘기세요.** 예컨대 **직원 이름, 직함, 계정명 같은 정보를 진단용으로 하나하나 넘기지 말고, 필요한 정보를 담은 `Employee` 객체를 넘기세요.**

```python
# 체인을 끊는다
def foo(bot: ChannelzBot, employee: Employee):
    bot.send_message(users=[employee.channelz_handle])


# 체인을 살린다
def foo(bot: ChannelzBot, employee: Employee):
    bot.send_message(employees=[employee])
```

*원서 예시 — 무엇을 넘기느냐가 나중에 쓸 수 있는 진단의 상한을 정한다*

> 이제 **유지 보수 담당자가 `send_message`의 진단을 개선하고 싶다고 한다면 먼저 리팩터부터 해야** 합니다. **귀찮아서 포기할 수도** 있고요.

**"나중에 좋은 에러를 쓸 수 있는가"가 지금 시그니처에 달려 있다**는 점이 요점이다. 계정명 문자열만 받은 함수는 **아무리 노력해도 "이 사람이 어느 팀인지"를 말할 수 없다.**

물론 **호출자 유연성과의 트레이드오프**다. 원서는 **시나리오로 이 논쟁을 푼다.**

- **직원이 아닌 사람에게 메시지를 보낼 일이 정말 있나?** **아마 없다.**
- **`Employees` 객체가 없는 레거시 영역이 있을까?** **있을 수 있다.** 그렇다면 **원본 사용자 계정명을 받는 레거시 버전의 `send_message`를 따로** 두면 된다. **객체가 있는 사용자는 좋은 진단을 받고, 나머지에게는 탈출구가 마련**된다.

### 구조화된 메타데이터를 붙인다

> [!WARNING]
> **에러 메시지를 데이터 포맷으로 만들지 않는다**
>
> 예외 객체에 구조화된 메타데이터 필드를 포함한다. 호출자가 데이터를 추출하려고 사람이 읽는 에러 메시지를 파싱하게 만들지 않는다.

> **호출자가 자기 에러 메시지를 직접 만들고 싶을 수 있다고 늘 가정**해야 합니다. 그러니 **메시지에 쓴 데이터는 전부 메타데이터에도 넣어두세요.**

그래서 채널즈는 **`ChannelzUserNotFoundError`에 `user` 속성**을 추가한다. **옵저버빌리티 팀이 누락된 사용자를 추출하고 싶어 할 수** 있기 때문이다.

### 추가 맥락을 끝까지 유지한다

> **컴파일러처럼 데이터 변환이 단계별로 이뤄지는 아키텍처에서는 여러 단계를 거친 뒤에야 에러를 발견하는 경우가 많습니다.** 이때는 **원래의 입력 맥락을 끝까지 유지하는 것이 매우 중요**합니다.

여기서 [이 장을 연 LaTeX 사례](./README.md)가 회수된다.

```mermaid
flowchart LR
    SRC["소스 코드<br/>줄 번호 · 공백 · 원본 토큰"]
    LEX["렉서"]
    PARSE["파서 · 이후 패스"]
    LOSS["맥락을 떼어내면<br/>underfull hbox 밖에 못 쓴다"]
    KEEP["맥락을 실어 보내면<br/>불필요한 줄바꿈이라고<br/>정확히 쓴다"]

    SRC --> LEX
    LEX -- "공백 · 줄 번호를 버림" --> LOSS
    LEX -- "출력에 충분한 정보를 담음" --> PARSE
    PARSE --> KEEP

    %% lint-ok: DEAD-END  두 갈래의 결과가 종착점이다
    %% lint-ok: NO-INBOUND  소스 코드가 흐름의 출발점이다
    classDef core fill:#93ad70,stroke:#5f7a44,color:#121a08
    classDef sys fill:#e9e5a8,stroke:#a99f4d,color:#26240c
    classDef muted fill:#dcdcd2,stroke:#a8a89c,color:#3a3a30
    class KEEP core
    class LEX,PARSE sys
    class SRC,LOSS muted
```

*렉서가 무엇을 버리느냐가 마지막 패스의 메시지 품질을 결정한다*

> **파서는 공백이나 줄 번호가 필요 없으니 렉서가 떼어낼 수 있습니다. 하지만 그렇게 해서는 안 됩니다.** 아마 그 경고는 **원본 소스 맥락을 잃어버린 상태에서** 던져졌을 겁니다. **그래서 쓸 만한 메시지를 쓸 길이 없어진** 거죠.

> **요즘 렉서는 출력물에 충분한 정보를 포함**하고 있어서, 이후 컴파일 단계가 훨씬 현대적인 환경을 제공할 수 있습니다.

```text
This is at the end of a block of text. \\
                                       ^^
Unnecessary \\ to end a paragraph on line 2.
```

**"파서가 필요로 하지 않는다"와 "버려도 된다"는 다르다.** 진단은 **파싱이 실패한 뒤에 쓰이므로**, 파싱에 불필요한 정보야말로 **진단에 필요한 정보**인 경우가 많다.

> [!IMPORTANT]
> **정보 체인을 끝까지 유지한다**
>
> 중간 계층이 원본 데이터와 사용자 맥락을 버리면 마지막 계층은 좋은 진단을 만들 수 없다. 진단에 필요한 정보를 구조화해 다음 단계로 전달한다.

> **최고의 에러는 시스템 정보와 사용자 시나리오 정보를 코드 한 지점에 최대한 모았을 때** 만들어집니다. **이걸 가능하게 하는 게 에러의 프로그래밍 가능성**입니다.
