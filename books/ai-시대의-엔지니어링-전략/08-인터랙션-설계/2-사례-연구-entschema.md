# 사례 연구 - EntSchema

> [인터랙션 설계](./README.md)

## 빠른 복습
- **2010년대 초, 저자는 페이스북에서 소셜 네트워크 그래프의 데이터베이스 객체를 모델링하는 스키마 설계를** 이끌었다.
- **객체는 엔티티**라 부르며 **사용자, 게시물, 그룹, 이벤트**가 여기 속한다. **엣지는 친구 관계, 멤버십, 게시물 작성자 같은 연결**이다. 스키마 이름은 **EntSchema**('엔티티 스키마'의 줄임말).
- 북극성 시나리오 하나 — **스키마 작성: 모델을 만드는 사람은 표현 하나를 작성해 데이터베이스 스키마, 읽기 클래스, 쓰기 클래스를 한 번에 뽑아내고** 싶어 한다.
- **스키마에 데이터베이스 계층 바깥에서 쓸 정보가 거의 없다**는 점이 초기 버전의 특징이며, 그 덕에 **저장돼 있던 데이터베이스 표현에서 EntSchema를 자동으로 만들 수** 있었다.
- 그러나 **스키마 작성자만 페르소나는 아니었다.** **스키마를 읽고 쓰는 사람**, 특히 **객체 인스펙터를 쓰는 엔지니어**도 있었다.

> [!NOTE]
> **다른 페르소나를 뒤늦게 발견할 수 있습니다**
>
> 최초 사용자의 시나리오를 잘 풀었더라도, 같은 데이터를 읽고 운영하고 디버깅하는 사용자의 요구까지 계속 확인해야 합니다.

## 가장 단순한 버전

```python
class PostSchema(EntSchema):
    def db_config() -> DatabaseConfig:
        return (DatabaseConfig()
                .name("posts"))

    def fields(self) -> dict:
        return {
            "id": int64_field().primary_key(),
            "text": varchar_field(4096),
            "created": int64_field(),
            # ...
        }

    def edges(self) -> dict:
        return {
            # 한 작성자는 여러 Post를 가질 수 있다.
            "author": edge(UserSchema, cardinality=EdgeCardinality.ManyToOne),
            # ...
        }
```

*원서 예시 — 북극성이 '스키마 작성' 하나뿐일 때의 테이블 스테이크 버전*

이 정의 하나에서 넷이 만들어진다.

- **`id`, `text`, `created` 스키마를 가진 데이터베이스 테이블**
- **작성자와 게시물을 연결하는 엣지 데이터베이스 테이블**
- **파이썬에서 읽기 접근에 쓰는 `Post` 클래스**
- **파이썬에서 `Post`를 만들고 편집하는 또 다른 클래스 `PostMutator`**

```python
class Post:
    @property
    def text(self) -> str: ...

    @property
    def created(self) -> str: ...

    @property
    def id(self) -> int: ...

    async def fetch_author(self) -> User: ...
```

*생성된 읽기 클래스*

## 단순함이 준 이득

> **스키마에 데이터베이스 계층 바깥에서 쓸 정보가 거의 없다는 점을 눈여겨보세요. 시나리오 하나를 푸는 데 필요한 최소한만 적혀** 있습니다.

> **EntSchema를 도입할 당시 이미 데이터베이스와 코드베이스에는 수많은 엔티티가 손으로 만들어져** 있었습니다. **단순한 데이터베이스 수준 표현을 유지하는 큰 장점은 여기에** 있어요. **저장돼 있던 데이터베이스 표현에서 EntSchema를 자동으로 만들 수 있다는 점**입니다. **간단한 스크립트만 있으면 아주 큰 코드베이스의 마이그레이션이 한결 가벼워집니다.**

```mermaid
flowchart LR
    DB["기존 데이터베이스 표현"]
    SCRIPT["간단한 스크립트"]

    MIG["대규모 코드베이스 마이그레이션"]

    DB --> SCRIPT
    SCRIPT --> SCHEMA
    SCHEMA --> MIG

    %% lint-ok: DEAD-END  마이그레이션이 이 이득의 귀결이다
```

*스키마에 DB 밖 정보가 없다는 제약이 자동 변환을 가능하게 했다*

**"정보를 덜 담았기 때문에 자동으로 채울 수 있었다"** 는 역설이 이 사례의 첫 교훈이다. 그런데 **바로 그 단순함이 다음 문제를 만든다.**

## 그런데 다른 페르소나가 있다

> **스키마 작성자만 페르소나는 아니었습니다.** **엔지니어들은 프로덕션 이슈를 디버깅하려고 객체 인스펙터를 자주** 썼습니다.

> **스키마 작성자에게 좀 더 풍부한 타입 정보를 요청**해본다고 가정해 봅시다. **`created` 필드가 단순 정수가 아니라 타임스탬프라고 명시**하게 하는 거죠. 이제 **`Post` 객체를 디버깅할 때 사용자는 사람이 읽을 수 있는 시간 포맷**을 보게 됩니다.

> **하지만 이게 단순한 스코프 크리프였을까요?** **점진적 전략은 위험했습니다. 쉬운 길로 가서 저수준 버전만 출시했다면, 더 풍부한 타입 정보를 나중에 추가하기는 어려웠을** 겁니다.

**["작게 시작하라"](../07-시뮬레이션을-통한-제품-탐색/7-첫-마일스톤-정하기.md) 는 조언과 정면으로 부딪히는 지점**이다. 스키마에 **한 번 정보를 안 받고 출시하면, 나중에 받으려면 기존 스키마 전부를 고쳐야** 한다 — [7절이 말하는 "함정문 결정"](./7-단계적으로-만들기와-실험-버전.md)이다.

> 이 사례 연구는 **스키마 작성자가 EntSchema에 어떤 추가 정보를 넣어야 하는지, 왜 그래야 하는지를** 따라갑니다. **장이 끝날 즈음이면 앞서 보여드린 `PostSchema`가 더 많은 시나리오에 맞는 모습으로 탈바꿈**해 있을 거예요.

## Go의 Ents

> **`ent`라는 인기 있는 오픈소스 Go 프레임워크가 EntSchema에서 영감을 받았습니다.** 전반적인 감을 잡고 싶다면 둘러보세요. **다만 필드 타입 시스템은 메타 내부 버전만큼 풍부하지는 않습니다.**
