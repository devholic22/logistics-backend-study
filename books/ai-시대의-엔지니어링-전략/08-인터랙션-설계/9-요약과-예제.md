## 빠른 복습
- **EntSchema는 시나리오 활용 덕분에 안전하고 생산적인 개발자 경험을 제공**할 수 있었다. **3의 법칙은 빈말이 아니었다.**
- **스키마 작성자에게서 잡아낸 지식으로 굴러가는 일반 개발 플랫폼으로 진화**했다 — **웹 문서, 객체 인스펙터, 데이터 마이그레이션 도구, 데이터 무결성 체크, GraphQL 스키마 생성** 등.
- **처음에는 개발자 생산성을 높이기 위한 개선 사항으로 시작했지만, 일부 기능이 미션 크리티컬해지면서 결국 모든 엔티티에 필수**가 됐다.

> [!IMPORTANT]
> **안전하고 생산적인 경로를 기본으로 만드세요**
>
> 좋은 설계는 사용자가 올바른 선택을 자연스럽게 발견하게 하고, 위험한 선택에는 알맞은 마찰과 검증을 둡니다.

## 8.7 요약

| 조언 | 내용 |
| --- | --- |
| **원칙에 얽매이지 말라** | **어떤 기능을 만들지 결정하려면 사용자 페르소나와 시나리오를 구체적으로 살펴봐야** 한다 |
| **기표를 살펴라** | **사용자가 자연스럽게 올바른 선택을 하도록 유도하는 환경**을 만들기 위해 **가장 좋은 어포던스는 강조하고, 좋지 않은 어포던스는 드러나지 않게** 한다 |
| **결정을 점검하라** | **사용자가 내리는 결정이 중요한 결정인지, 검증됐는지, 올바른 페르소나가 다루고 있는지** 확인한다 |
| **낙관도 비관도 아니게** | **시나리오를 만들어 기능의 장점과 달갑지 않은 단점을 함께** 부각한다 |

**시간과 반복이라는 요소를 더한 조언**도 넷이다.

- **집중할 때 가장 잘 해내니, 우선순위가 높고 집중할 가치가 있을 때 기능을** 만든다.
- **함정문 결정을 피하려면 경계를 세운다.** **데이터를 모으고, 미래 개발 선택지를 살리는 방식으로 기능 접근을 제한**한다.
- 동시에 **3의 법칙을 기억**한다. **설득력 있는 시나리오 여럿이 뒷받침하지 않는 기능이나 확장 지점에 시간을 쏟지** 않는다.
- **결정이 안 서고 의심스러울 때는 빼둔다.** **다행히 나중에, 상황이 분명해졌을 때 추가할 수** 있다.

> **경험칙일 뿐이지만, 제 경험에서는 이런 용어로 어려운 제품 선택을 고민할 때 저와 팀에 명료함과 확신이 생겼어요.**

## 8.8~8.9 예제와 답안

**비밀번호 관리자**를 만드는 예제다. **타깃 페르소나는 모든 앱과 웹사이트에 사용할 고품질 비밀번호를 일일이 외우지 않고도 안전하게 저장하는 게 목표인 디지털 네이티브**이며, **비밀번호를 만들고, 수정하고, 저장하기 쉬우면서도 오용하기는 어려워야** 한다. **패스키는 더 현대적이고 안전하지만 아직 덜 쓰이므로 빼둔다.**

### 1) 신호등 어포던스

| 등급 | 시나리오 |
| --- | --- |
| **녹색** | **사용자가 해당 앱에 고유하고 자동으로 생성된 강력한 랜덤 비밀번호를 선택** |
| **노란색** | **자신만의 기억하기 쉬운 비밀번호를 입력**하지만 **비밀번호를 학습한 알고리즘에 추측당할 수** 있다. 또는 **다른 사이트와 공유하는 비밀번호로 확인될 경우 '크리덴셜 스터핑' 공격에 노출** |
| **빨간색** | **기존 로그인을 입력할 때, 데이터 유출로 이미 손상됐다고 알려진 비밀번호·이메일 조합을 사용** |

표를 읽는 법. 세 등급이 **"비밀번호의 세기"가 아니라 "노출 위험"** 으로 갈린다. 노란색이 위험한 이유도 **재사용** 때문이지 복잡도 때문이 아니다.

### 2) 녹색을 강조하는 설계

> **자기 비밀번호를 직접 타이핑하는 건, 짧고 익숙한 비밀번호라면 꽤 쉽습니다.** 그 말은 **비밀번호 관리자의 자동 생성 기능을 더 쉽고 더 발견하기 쉽게 만들어야 한다**는 뜻입니다.

**1패스워드의 브라우저 플러그인**이 하는 일이다.

| 조치 | 무엇을 막나 |
| --- | --- |
| **비밀번호 양식을 자동으로 감지하고, 비밀번호 관리자를 쓰라는 다이얼로그**를 띄운다 | **발견 가능성 역전** — 오작동 신호등 |
| **타이핑보다 쉬운 원클릭으로 강력한 비밀번호 생성 옵션**을 제시 | **사용 편의성의 저하** |
| **일부 웹사이트의 기호·길이 요건 같은 제약을 사용자가 설정**할 수 있게 | **임의로 취약한 비밀번호를 직접 만드는 상황으로 빠지는 것** |

첫 줄이 [오작동 신호등](./4-최소-저항-경로와-오작동-신호등.md)을 정면으로 겨냥한 조치다.

표를 읽는 법. 셋째 줄이 미묘하다. **사이트가 요건을 걸어 자동 생성이 실패하면, 사용자는 직접 만들기로 돌아간다** — **녹색 경로가 막히는 순간 노란 경로가 최소 저항 경로**가 된다.

### 3) 도메인 데이터베이스에 3의 법칙 적용

**웹사이트 도메인과 해당 도메인의 최신 보안 정보를 함께 저장하는 데이터베이스**를 직접 만들지, **피싱 의심 도메인 목록을 제공하는 제3자 데이터베이스에 의존**할지의 문제다.

우리 데이터베이스에는 **검증된 안전 도메인, 데이터 유출 이력이 있는 도메인, 제3자가 이미 제공한 피싱 도메인 정보**가 담기고, **도메인을 손상된 비밀번호 목록에 매핑**할 수도 있다.

| 유스 케이스 |
| --- |
| **피싱 의심 도메인이 사용자 이름과 비밀번호를 요구할 때, 빨간색 다이얼로그로 경고** |
| **자격 증명을 넘기려는 도메인이 해당 자격 증명이 원래 저장된 도메인이 아닌 미검증 도메인일 때, 추가 경고** |
| **사용자 이름·비밀번호가 데이터 유출로 노출됐을 가능성이 있을 때 경고.** **다른 웹사이트와 앱에 같은 비밀번호를 공유한 경우까지 포함** |
| **어떤 도메인에서 충분히 많은 사용자가 특정 제약을 걸고 비밀번호를 생성하면, 그 패턴을 기록해 해당 사이트에 그런 제약이 있다고 추론**하고, **이후 사용자에게는 그 제약에 맞춰 자동으로 생성** |

표를 읽는 법. 마지막 줄이 [바로 앞 문제의 셋째 조치](./9-요약과-예제.md#2-녹색을-강조하는-설계)와 이어진다 — **사용자가 수동으로 설정하던 것을 데이터베이스가 대신 알아낸다.** 확장 가능한 버전이 **원래 목적(피싱 경고) 밖의 시나리오**까지 열어 주는 사례다.

> 물론 **이러한 분석만으로 결정을 내리기에는 충분하지 않습니다.** 하지만 **이처럼 여러 시나리오를 살펴보면, 자체적으로 확장 가능한 데이터베이스를 구축하고 이를 회사의 핵심 역량으로 삼을지 검토해 볼 가치는 있어** 보입니다.
