# 프로덕트 아키텍처

> [AI 시대의 엔지니어링 전략](../README.md)

## 보기엔 그럴싸한데 돌아가지 않는 물건

> **소프트웨어에서 의미 있는 요구 사항을 손에 쥐는 일은 드뭅니다.** 손에 쥐었다 해도 **성공의 잣대는 단 하나입니다. 바로 우리 솔루션이 고객의 끊임없이 바뀌는 문제 인식을 풀어주는가**입니다.
> — 제프 앳우드

**기능 요구 사항은 사용자가 원하는 바를 수행할 수 있도록 제품의 어포던스가 갖춰야 할 목표**들이며, **[8장](../08-인터랙션-설계/README.md) 전체가 사실 이에 관한 이야기**였다.

> **여기에만 매달리면 결국 포템킨 마을 같은 소프트웨어가 남습니다. 보기엔 그럴싸한데 실제로는 돌아가지 않는 물건**이죠. 그래서 **NFR도 함께** 살펴야 합니다.

**NFR(비기능 요구 사항)에 드는 것** — **비용, 확장성, 지연 시간, 처리량, 데이터 일관성, 탄력성, 가용성**. **프라이버시와 보안도 빼놓을 수 없는데, 이 책에서 깊이 다루지는 않는다.**

> **NFR은 그 자체로 사용자 목표가 아닙니다. 목표를 이루는 수단입니다.** **제대로 작동하지 않을 때만 사용자 눈에 들어오는 항목**이기도 합니다.

> [!IMPORTANT]
> **NFR을 사용자 목표에서 출발시키세요**
>
> 지연 시간·가용성·일관성·확장성은 독립적인 기술 목표가 아니라 사용자가 과업을 성공적으로 끝내기 위한 수단입니다.

## 프로덕트 아키텍처란

> 저는 이 합성을 **프로덕트 아키텍처**라고 부릅니다. **사용자와 비즈니스 제약이라는 맥락 위에서 수행하는 시스템 설계**를 뜻합니다.

> 저는 이 주제를 좋아합니다. **책 전체에서 가장 엔지니어링 냄새가 짙으면서도, 프로덕트 사고의 힘을 여전히 빌려야** 하거든요. **사용자 중심 사고와 시스템 중심 사고를 완벽하게 융합하는 작업**입니다. 게다가 **프로덕트 매니저나 다른 역할이 설계를 도와주기 가장 어려운 영역**이기도 합니다.

```mermaid
flowchart LR
    UX["빠르고 안정적인 사용자 경험<br/>지연 시간 · 가용성<br/>데이터 일관성"]
    SCALE["확장성 요소<br/>처리량 · 격리"]
    GOV["데이터 거버넌스<br/>컴플라이언스 · 보안<br/>프라이버시"]
    PA["프로덕트 아키텍처"]

    UX --> PA
    SCALE --> PA
    GOV -. "다루지 않음(범위 밖)" .-> PA

    %% lint-ok: DEAD-END  세 범주가 모이는 개념이 종착점이다
    %% lint-ok: NO-INBOUND  세 범주가 각각 출발점이다
    classDef core fill:#93ad70,stroke:#5f7a44,color:#121a08
    classDef sys fill:#e9e5a8,stroke:#a99f4d,color:#26240c
    classDef muted fill:#dcdcd2,stroke:#a8a89c,color:#3a3a30
    class PA core
    class UX,SCALE sys
    class GOV muted
```

*이 장이 다루는 두 범주와, 생략한 한 범주*

| 범주 | 언제 체감되나 |
| --- | --- |
| **빠르고 안정적인 사용자 경험** | **지연 시간, 가용성, 데이터 일관성** |
| **확장성 요소** | **많은 사용자가 동시에 시스템을 쓸 때 비로소 체감되는 처리량과 격리** |
| **데이터 거버넌스**(생략) | **컴플라이언스, 보안, 프라이버시.** **여기서도 프로덕트 사고의 힘은 잘 드러난다** |

표를 읽는 법. 둘째 줄의 **"비로소 체감되는"** 이 확장성 문제의 성격을 말한다 — **혼자 쓸 때는 아무 문제가 없다.** 그래서 [시뮬레이션](./7-확장성과-확장성-시뮬레이션.md)이 필요하다.

## 시나리오에서 아키텍처 결정까지

기술 지표를 먼저 정하지 말고 **누가 어떤 작업을 언제까지, 어떤 결과로 완료해야 하는지** 정의한 뒤 그 경험을 지킬 보장을 선택한다. 아래는 본문 내용을 실무 검토 순서로 재구성한 예시이며, 실제 서비스의 검증 결과나 권장 임계값을 뜻하지 않는다.

| 사용자 시나리오의 질문 | 사용자에게 약속할 결과 | 먼저 관찰할 신호 | 설계에서 검토할 선택 |
| --- | --- | --- | --- |
| 사용자가 결제를 제출하고 결과를 기다리는가? | 성공·거절·처리 중 상태를 오해하지 않고 확인한다 | 결제 시나리오 완료 시간, 실패 결과 통지 시간, 구간별 트레이스 | 동기 검증 경계, 비동기 후속 처리, 타임아웃 및 재조회 |
| 브라우저에서 요청 자체가 출발하지 못하는가? | 사용자가 화면을 열고 주요 행동을 끝낼 수 있다 | 클라이언트 오류, 요청 도달률, 사용자 흐름 성공률 | 클라이언트 계측, 복구 가능한 UX, 부분 장애 격리 |
| 여러 사용자가 같은 주문을 수정하는가? | 확정한 주문 항목과 금액이 누락·중복되지 않는다 | 충돌·중복·재시도 비율, 최종 주문 불일치 건수 | 멱등성 키, append 방식, 확정 시점 잠금, 사후 무결성 검사 |
| 특정 고객의 요청이 급증하는가? | 다른 고객의 핵심 작업이 함께 중단되지 않는다 | 고객별 성공률·대기 시간, 큐 적체, 자원 포화도 | 테넌트 격리, 백프레셔, 한도 정책, 고충실도 시뮬레이션 |

이 표에서 **관찰 지표는 사용자 약속의 대체물이 아니다.** 백엔드 API 성공률이 높아도 화면이 깨지면 사용자 과업은 실패하고, 데이터베이스 트랜잭션이 성공해도 다른 참여자의 변경이 누락되면 주문은 올바르지 않다.

### 결정과 검증을 기록하는 순서

1. **시나리오**: 행위자·동기·시작과 종료 조건을 적고, 실패했을 때 사용자에게 보이는 문제를 구체화한다.
2. **보장과 범위**: 지연 시간·가용성·일관성·격리 중 무엇이 필요한지, 누구에게 어디까지 보장할지 정의한다. 목표 수치는 근거가 확보되기 전까지 가설로 둔다.
3. **대안과 비용**: 계층별 변경 지점, 지연·복잡도·운영 비용과 장애 시 동작을 비교한다. 선택 근거는 [ADR 템플릿](../../../docs/adr/template.md)에 따로 남긴다.
4. **실험과 관측**: 시나리오 지표를 분산 추적·클라이언트 계측·재현 가능한 부하 시뮬레이션과 연결한다. 실험 환경과 미검증 항목을 명시한다.
5. **피드백**: 실제 사용자 결과가 가설과 다르면 요구사항과 설계 결정을 다시 검토한다.

> **예시: 외부 WMS 재고 조정** — 관리자가 재고 변경을 요청한 뒤 외부 WMS의 처리 응답이 늦거나 콜백이 유실된다고 가정한다. 이때 중요한 것은 단순 API 응답 시간이 아니라 **요청자가 처리 중·완료·실패를 구별하고, 중복 재시도로 재고가 두 번 조정되지 않으며, 최종 수량을 검증할 수 있는가**다. 멱등성·상태 조회·대사 절차는 이 사용자 약속에서 도출할 수 있는 *설계 후보*이며, 특정 서비스에 이미 구현됐다는 의미는 아니다.

각 품질 속성의 구체적인 논거와 예시는 [지연 시간](./3-지연-시간.md), [가용성](./4-가용성.md), [데이터 일관성](./5-데이터-일관성.md), [확장성 시뮬레이션](./7-확장성과-확장성-시뮬레이션.md)에서 이어진다.
