# 그러면 어떻게 매핑할 것인가

> [IllegalArgumentException은 400 Bad Request인가](./README.md)

## 빠른 복습
- 기준은 두 줄이다 — **클라이언트 요청이 잘못된 경우가 명확하면서 이를 사전에 예측해 처리할 수 있다면 400**, **예상치 못한 예외나 서버 내부 로직 오류로 처리가 중단된 경우는 500.**
- **스프링은 별도 매핑이 없는 예외에 500을 응답**한다. 그러니 **기본값을 500에 두고, 원인이 클라이언트의 잘못으로 판명되면 그때 4xx로 바꾸는** 방향이 좋다.
- **비즈니스 예외**('최소 주문 금액 미달' 등)는 400, **시스템 예외**(DB 연결 실패, API 연동 실패, `NullPointerException`, 라이브러리 내부 오류)는 5xx가 적절하다.
- **예측 가능한 시스템 예외는 대체 응답(Fallback Response)을 제공**해 5xx를 회피하면서 모니터링할 수 있게 설계하는 것이 좋다.
- **`IllegalArgumentException`·`IllegalStateException` 같은 범용 예외 대신 `BusinessException`, `FieldNameDuplicatedException` 같은 커스텀 예외를 정의**하고 거기에 400을 매핑한다.

## 기준 ① 예상 못 한 상황은 5xx, 명백한 클라이언트 잘못은 4xx

| 상황 | 응답 |
| --- | --- |
| **클라이언트 요청이 잘못된 경우가 명확하면서 이를 사전에 예측해 처리할 수 있다** | **400** |
| **예상치 못한 예외나 서버 내부 로직 오류로 처리가 중단되었다** | **500** |

표를 읽는 법. 400의 조건에 **"명확하면서"와 "사전에 예측해 처리할 수 있다"** 는 두 단서가 붙어 있다. **애매하면 400이 아니다**는 뜻이며, 이것이 곧 기본값을 어디에 둘지를 정한다.

> **스프링 프레임워크는 별도의 매핑이 없는 예외가 발생할 경우 500 에러를 응답**하기에, **문제를 조치하며 원인이 클라이언트의 잘못으로 판명되면 4xx를 응답하도록 수정**하는 게 좋다.


*모르는 것은 500으로 두고, 알게 된 만큼만 4xx로 옮긴다*

**안전한 방향으로 틀리도록 기본값을 잡는 것**이 이 지침의 요지다. 500으로 잘못 내보내면 **경보가 한 번 더 울릴 뿐**이지만, 400으로 잘못 내보내면 **아무 일도 일어나지 않는다.**

## 기준 ② 비즈니스 예외와 시스템 예외를 나눈다

| 종류 | 언제 발생하나 | 응답 |
| --- | --- | --- |
| **비즈니스 예외** | **'최소 주문 금액 미달'과 같이 클라이언트의 입력이나 조건이 맞지 않을 때** | **400** |
| **시스템 예외** | **DB 연결 실패, API 연동 실패, `NullPointerException`, 라이브러리 내부 오류** | **5xx** |

표를 읽는 법. **비즈니스 예외는 도메인 규칙이 거절한 것**이고, **시스템 예외는 규칙에 닿지도 못하고 무너진 것**이다. 앞의 것은 **설계된 결과**이고 뒤의 것은 **설계 밖의 사고**다. `IllegalArgumentException`이 곤란한 이유는 **양쪽 모두에서 튀어나오기 때문**이다.

> **예측 가능한 시스템 예외는 대체 응답(Fallback Response)을 제공하여 5xx 응답을 회피하고 모니터링할 수 있도록 설계**하는 게 좋다.

**"회피하고, 그러나 모니터링한다"** 는 두 요구를 함께 읽어야 한다. 사용자에게는 무너진 화면 대신 대체 응답을 주되, **그 일이 일어났다는 사실 자체는 지표로 남긴다.** 응답 코드가 200이 되었다고 문제가 없어진 것은 아니다.

## 기준 ③ 커스텀 예외로 클라이언트의 잘못을 명확히 전달한다

> **`IllegalArgumentException`이나 `IllegalStateException` 같은 범용 예외 클래스 대신 `BusinessException`, `FieldNameDuplicatedException`과 같은 커스텀 예외를 정의**하고 **400 Bad Request 응답을 매핑**한다. 이렇게 정의된 커스텀 예외는 **비즈니스 로직에서 클라이언트의 잘못이 명확할 때 발생**시킨다.

```java
@Getter
public class BusinessException extends RuntimeException {

    // 클라이언트 개발자가 예외 상황을 식별할 수 있는 값
    private final String code;

    // 클라이언트 개발자가 예외 상황을 이해하는 데 도움이 되는 정보
    private final Map<String, Object> arguments;

    public BusinessException(String code) {
        this(code, null);
    }

    public BusinessException(String code, String message) {
        super(message);
        this.code = code;
        this.arguments = new HashMap<>();
    }

    protected void addArgument(String key, Object value) {
        arguments.put(key, value);
    }
}
```

*원서 예시 — 400으로 나갈 예외들의 공통 부모*

**필드 두 개가 이 클래스의 전부**이며, 둘 다 **클라이언트 개발자를 위한 것**이다. `code`는 **기계가 분기할 수 있는 식별자**이고, `arguments`는 **사람이 원인을 이해하도록 돕는 부가 정보**다. 메시지 문자열 하나만 던지는 것과 달리, **받는 쪽이 문자열을 파싱하지 않아도 된다.**

```java
public class InvalidExpressionException extends BusinessException {

    public InvalidExpressionException(int position, String hint) {
        super("expression.invalid", "표현식이 올바르지 않습니다.");
        addArgument("position", position);
        addArgument("hint", hint);
    }
}
```

*구체적인 예외는 상속으로 만든다 — 생성자가 곧 그 오류의 명세다*

```java
@RestControllerAdvice
public class GlobalDefaultExceptionHandler {

    @ResponseStatus(HttpStatus.BAD_REQUEST)
    @ExceptionHandler(BusinessException.class)
    public ErrorResponse onException(BusinessException exception) {
        // ...
    }
}
```

*핸들러는 부모 타입 하나만 받는다*

**더 구체적인 예외 클래스를 정의하고 싶으면 상속하면 되고**, 핸들러는 그대로 둔 채 **어디서든 `BusinessException`이나 그 하위 예외가 발생하면 400을 응답**하게 된다.

여기서 400으로 나가는 조건이 바뀌었다는 점이 핵심이다. **"어떤 클래스의 예외인가"가 아니라 "우리가 클라이언트 잘못이라고 선언한 예외인가"** 가 기준이 되었다. **판단을 던지는 쪽에서 내리므로**, 핸들러는 더 이상 추측하지 않는다.

이것은 [『좋은 코드의 기준』 2장](../../내-코드가-불안한-개발자를-위한-좋은-코드의-기준/02-움직이는-코드에서-뜻을-전하는-코드로/4-코드로-도메인-지식-표현하기.md#동작도-도메인-객체-안에)이 말한 **의미를 타입에 담는 일**과 같다. `IllegalArgumentException`은 **"인자가 이상하다"** 까지만 말하지만, `InvalidExpressionException`은 **"클라이언트가 보낸 표현식이 규칙에 어긋난다"** 고 말한다. 뒤의 문장에만 **응답 코드를 정할 정보가 들어 있다.**

## 요약 및 결론

- **4xx는 클라이언트 오류다.** 클라이언트의 잘못된 요청일 때 사용한다.
- **5xx는 서버 에러다.** 서버 내부 문제로 요청을 처리하지 못할 때 사용한다.
- **서버 문제가 4xx로 잘못 응답하면 클라이언트 잘못으로 오인하여 빠른 대응이 어려워질 수 있다.**
- **`IllegalArgumentException`은 서버 버그로도 발생할 수 있으므로, 무조건 400으로 매핑하면 서버 문제를 뒤늦게 발견할 위험**이 있다.
- **400 응답이 필요한 상황에는 `BusinessException` 같은 커스텀 예외를 정의하여 명확하게 매핑**하는 게 좋다.

> **상태 코드를 명확하게 매핑하면 오류에 빠르게 대응할 수 있고 API 유지보수도 장기적으로 간소화**할 수 있다.
