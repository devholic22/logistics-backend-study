# 동적 출고 예정 시각 — 시뮬레이션으로 검증하기

> [B마트 OMS의 물류주문관리를 통한 출고 최적화](./README.md)

## 빠른 복습
- 과제의 핵심은 **주문별 출고 예정 시각을 동적으로 계산하고, 실제 운영 환경과 유사한 방식으로 시뮬레이션을 설계하며, 예측 가능하고 테스트할 수 있는 비즈니스 로직으로 구현하는 것**이었다.
- 출고 예정 시각은 **주문–출고–배송 흐름 전반에 사용**되므로 **시뮬레이션의 신뢰도와 재현성 확보가 가장 중요한 포인트**였다.
- 시뮬레이션 설계의 핵심은 **실제 시스템에서 발생하는 도메인 이벤트의 흐름을 최대한 그대로 재현**하는 것 — **이벤트 통합 후 시간순 정렬**, **실행 흐름의 선형화와 외부 의존 제거(WMS는 Mock)**.
- 비동기 문제는 **비동기 큐가 완전히 비워질 때까지 다음 이벤트 처리를 멈추는** 방식으로 해결했다.
- 시간은 **`LocalDateTime.now()` 대신 외부에서 주입**하고, 중간 로직에서는 **DI 기반 시간 프로바이더**를 썼다.
- 시뮬레이션과 실제의 간극은 **주문번호 기반 파티셔닝을 센터 코드 기반으로 바꾸어** 줄였다.
- 성과 — **출고 예정 시각과 실제 출고 완료 시각의 편차(표준편차) 35.7% 감소**, **라이더 평균 대기 시간 86.67% 이상 감소.**

## 시뮬레이션을 어떻게 설계했나

> **실제 시스템에서 발생하는 도메인 이벤트의 흐름을 최대한 그대로 재현하는 것이 핵심**이다.

| 방법 | 내용 |
| --- | --- |
| **이벤트 통합 및 시간순 정렬** | **주문·출고·배달에서 발생한 이벤트 데이터를 통합**하고 **시간순으로 정렬**해 시뮬레이션의 처리 흐름을 결정 |
| **실행 흐름의 선형화 및 외부 의존 제거** | 실제 환경은 비동기이지만 **시뮬레이션에서는 순차적으로 이벤트를 처리.** **WMS 같은 외부 시스템의 응답은 내부에서 Mock 처리**해 외부 의존 없이 테스트 가능하게 구성 |

표를 읽는 법. 두 줄 모두 **"현실을 단순화한다"** 가 아니라 **"현실의 순서를 고정한다"** 는 조치다. 재현성이 목적이므로 **매번 같은 순서로 같은 일이 벌어지게** 만드는 것이 우선이다.

```mermaid
flowchart LR
    EV["주문 · 출고 · 배달 이벤트 통합"]
    SORT["시간순 정렬"]
    STEP["이벤트 순차 처리"]
    WAIT["비동기 큐가 빌 때까지 대기"]
    MOCK["WMS 응답 Mock"]
    CALC["출고 예정 시각 산정"]

    EV --> SORT
    SORT --> STEP
    STEP --> WAIT
    WAIT --> CALC
    MOCK -. "외부 응답 대체(실 호출 없음)" .-> STEP
    CALC -- "다음 이벤트" --> STEP

    %% lint-ok: DEAD-END  Mock은 외부 응답을 대체하는 입력이므로 들어오는 흐름 없이 점선으로만 연결된다
    %% lint-ok: NO-INBOUND  같은 이유로 Mock 노드에는 인바운드가 없다
    classDef core fill:#93ad70,stroke:#5f7a44,color:#121a08
    classDef sys fill:#e9e5a8,stroke:#a99f4d,color:#26240c
    classDef muted fill:#dcdcd2,stroke:#a8a89c,color:#3a3a30
    class STEP,WAIT core
    class EV,SORT,CALC sys
    class MOCK muted
```

*시뮬레이션 루프 — 한 이벤트의 비동기 작업이 모두 끝난 뒤에야 다음 이벤트로 넘어간다*

## 비동기 처리 이슈

**실제 프로덕션에서는 출고 요청 외에도 여러 단계에서 비동기 작업이 발생**한다. 여기서 문제가 생긴다.

- **출고 요청 자체가 비동기로 처리되면서 특정 로직을 수행하고 WMS와 통신**한다.
- **비동기 작업들이 완료되기 전에 다음 이벤트가 처리되면, 아직 반영되지 않은 상태로 계산이 진행되어 결과가 잘못될 수 있다.**
- **시뮬레이션 환경에서는 WMS 응답을 기다릴 수 없고**, 다음 이벤트는 **미리 수집한 이벤트를 순차적으로 처리**하기 때문에 **비동기 작업이 모두 완료되기 전에 다음 이벤트가 실행되면 문제가 발생할 수밖에 없다.**

해결은 명확하다.

> **시뮬레이션에서는 모든 비동기 작업이 완료될 때까지 기다렸다가 다음 이벤트를 처리하도록 흐름을 제어**했다. **비동기 큐가 완전히 비워질 때까지 다음 이벤트 처리를 멈추어, 프로덕션 환경과 비슷한 순서로 이벤트가 처리되도록** 만들었다.

**"기다림"을 시뮬레이션이 대신 만들어준 것**이다. 프로덕션에서는 시간이 흐르며 자연히 채워지는 간격을, 시뮬레이션에서는 **큐가 비었는지 확인하는 조건**으로 대체했다.

## 시간을 재현하는 방법

> 시뮬레이션에서 중요한 것은 **과거의 상태를 정확히 재현**하는 것이다.

- **`LocalDateTime.now()`는 매번 값이 달라지기에**, **메서드 시그니처를 수정해 시각을 외부에서 주입**하도록 했다.
- **중간 처리 로직 시점의 현재 시각이 필요한 경우에는 DI(Dependency Injection) 기반의 시간 프로바이더를 활용**했다.

**시간이 숨은 입력**이라는 것이 요점이다. 시각을 함수 안에서 읽으면 그 함수는 **같은 인자에 다른 답을 주는 함수**가 되어, [앞 과제가 세운 결정성 원칙](./2-피크매니지먼트-기술-방향.md#비즈니스-규칙을-예측-가능하게-만든-방법)이 무너진다. 시각을 파라미터나 프로바이더로 밖에 내놓는 순간 **테스트가 과거를 지정할 수 있게 된다.**

이 처방은 [『아키텍트 첫걸음』 5.2의 단위 테스트](../../아키텍트-첫걸음/5-품질-보증과-테스트/2-기능-테스트-자동화.md#단위-테스트)가 말한 **"테스트하기 어려운 코드는 대개 의존을 안에서 만드는 코드"** 와 정확히 같은 진단이다.

## 시뮬레이션과 실제 환경의 차이를 조율하기

| | 전제 |
| --- | --- |
| **시뮬레이션** | 주문이 **순차적으로 출고 요청**되고 그 흐름에 따라 출고 예정 시각이 계산된다 |
| **실제** | 출고 요청이 **재고 확인, 파티션 처리 등 다양한 요인으로 인해 반드시 순차적으로 진행되지 않는다** |

표를 읽는 법. **간극을 시뮬레이션 쪽에서 메우지 않고 프로덕션 쪽을 바꿨다**는 점이 이 대목의 특이한 선택이다.

- **기존에는 주문번호 기반 파티셔닝으로 출고 요청을 처리**했는데, 이 경우 **재고 충돌이나 동시성 이슈로 예측할 수 없는 지연**이 발생했다.
- **개선된 구조에서는 센터 코드 기반 파티셔닝으로 변경**했다. 덕분에 **보다 예측 가능한 순차적 흐름이 만들어졌고**, **시뮬레이션의 전제와 실제 운영 간의 간극도 줄일 수 있었다.**

```mermaid
flowchart LR
    OLD["주문번호 기반 파티셔닝"]
    PROB["재고 충돌 · 동시성 이슈로<br/>예측할 수 없는 지연"]
    NEW["센터 코드 기반 파티셔닝"]
    GOOD["예측 가능한 순차 흐름"]

    OLD --> PROB
    PROB --> NEW
    NEW --> GOOD

    %% lint-ok: DEAD-END  개선 결과까지의 흐름이므로 마지막 노드에서 나가는 흐름이 없다
    classDef core fill:#93ad70,stroke:#5f7a44,color:#121a08
    classDef sys fill:#e9e5a8,stroke:#a99f4d,color:#26240c
    classDef muted fill:#dcdcd2,stroke:#a8a89c,color:#3a3a30
    class NEW,GOOD core
    class PROB sys
    class OLD muted
```

*파티션 키를 주문번호에서 센터 코드로 바꾸자 같은 센터의 요청이 한 줄로 정렬된다*

**같은 센터의 출고 요청이 같은 파티션으로 모이므로 그 안에서는 순서가 보장된다.** 재고 경합도 센터 안에서 일어나는 일이니, **경합하는 것끼리 같은 줄에 세운 셈**이다. [앞 과제가 PPC 단위로 병렬화한 것](./2-피크매니지먼트-기술-방향.md#ppc-단위로-쪼갠다)과 같은 기준이 여기서는 **파티션 키**로 나타난다.

## 성능 병목은 어디였나

**출고 요청이 순차적으로 이루어짐에 따른 성능 병목**이 우려되었지만, 실제로는 괜찮았다.

- **실제 병목은 시스템이 아니라 작업 인력, 피킹 속도, 현장 처리 능력 쪽에서 먼저 발생**한다.
- **출고 요청 지연이 시스템 병목의 주요 원인이 되는 경우는 거의 없었다.**
- **물리적 처리 한계가 먼저 도달하기 때문에, 시스템 복잡도와 병렬성에 과도하게 신경 쓰지 않아도 목표 성능을 충분히 만족**할 수 있었다.

**두 과제가 같은 결론에 따로 도달했다.** 순차화는 보통 성능을 포기하는 선택이지만, **병목이 사람 쪽에 있는 시스템에서는 포기할 것이 없다.** 대신 얻는 것은 **예측 가능성**이다.

## 정리 — 무엇을 구성했나

- **실제 운영 환경과 유사한 이벤트 흐름 시뮬레이션**
- **비동기 흐름을 제어할 수 있는 방식으로 순차적 처리**
- **시간 재현성 확보를 위한 시간 주입 및 Auditing 제어**
- **프로덕션–시뮬레이션 간 차이를 줄이기 위한 파티셔닝 구조 개선**
- **물리적 한계를 고려한 현실적 성능 판단 기준**

이로써 **출고 예정 시각을 정확하게 동적으로 계산**할 수 있었고, **예측 가능하고 테스트할 수 있는 구조로 안정적인 운영까지** 가능해졌다.

## 성과 및 효과

| 지표 | 결과 |
| --- | --- |
| **출고 예정 시각과 실제 출고 완료 시각 간의 편차**(표준편차 기준) | **35.7% 감소** |
| **라이더의 평균 대기 시간** | **86.67% 이상 감소** |

표에 제시된 집계값은 **출고 시각 편차와 라이더 평균 대기 시간이 모두 감소**했음을 보여준다. 다만 두 값만으로 대기 시간의 분포가 어떻게 바뀌었는지 또는 두 변화 사이에 어떤 인과 관계가 있는지까지 알 수는 없으므로, 그런 판단에는 원자료와 분포 분석이 추가로 필요하다.

## 마무리 및 향후 계획

- **B마트의 OMS는 주문 관리 시스템을 넘어 물류 운영의 실질적 퍼포먼스를 개선하는 플랫폼으로 진화**했음을 입증했다.
- **고객 배송 경험, 라이더의 업무 만족도, 현장 작업자의 처리 효율까지 함께 고려한 통합적 개선**을 달성했다.
- **최적화는 계속 진행 중**이다.

## 핵심 정리

- 출고 예정 시각은 **라이더 호출의 근거**이므로, 늦게 잡으면 호출과 배달이 지연되고 이르게 잡으면 라이더가 기다린다. **정확해야만 이득**이다.
- 고정 가산식을 **가용 인원 · 작업량 · 목표생산성**을 보는 동적 산정으로 바꿨다.
- 이 로직을 믿을 수 있게 한 것은 **재현 가능한 시뮬레이션** — 이벤트 시간순 정렬, 비동기 큐 비우기, 시간 주입, Mock.
- **시뮬레이션의 전제에 프로덕션을 맞추기 위해 파티션 키를 센터 코드로 바꿨다.** 검증 가능성을 위해 운영 구조를 손댄 사례다.
- 병목은 **시스템이 아니라 현장**이었고, 그 판단이 **과도한 최적화를 하지 않을 근거**가 되었다.
