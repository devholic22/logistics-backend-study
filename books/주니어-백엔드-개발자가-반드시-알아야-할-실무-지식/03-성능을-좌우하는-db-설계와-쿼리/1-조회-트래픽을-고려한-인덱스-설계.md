# 조회 트래픽을 고려한 인덱스 설계

> [성능을 좌우하는 DB 설계와 쿼리](./README.md)

> [!IMPORTANT]
> **인덱스는 실제 조회 트래픽을 기준으로 설계하세요**
>
> 선택도만 따르기보다 호출 빈도, 조건과 정렬, 데이터 분포를 함께 확인해야 합니다.

## 빠른 복습

- 인덱스는 테이블 크기만이 아니라 실제 filter·정렬·호출 빈도를 기준으로 설계한다.
- 선택도는 중요한 기준이지만 자주 찾는 값의 분포와 업무 패턴이 더 중요할 수 있다.
- 복합 인덱스의 컬럼 순서와 커버링 여부는 대상 쿼리의 실행 계획으로 검증한다.
- 인덱스는 조회를 빠르게 하지만 쓰기, 저장공간과 운영 비용을 늘린다.

일반적인 서비스는 쓰기보다 조회 비율이 높은 경우가 많다. 테이블을 설계할 때는 데이터 크기만 볼 것이 아니라 어떤 조건과 정렬로 얼마나 자주 조회하는지도 함께 고려해야 한다.

인덱스가 필요한지는 다음 요소의 조합으로 판단한다.

- 테이블의 현재 크기와 증가 속도
- 쿼리 호출 빈도와 피크 트래픽
- 조건에 맞는 행의 비율과 실제 스캔 행 수
- 정렬, 그룹화와 페이지네이션 방식
- 읽기·쓰기 비율과 허용 가능한 응답 시간
- DB buffer pool에 데이터와 인덱스가 얼마나 올라오는지

행 수가 적으면 풀 스캔이 인덱스 탐색보다 빠를 수도 있다. 반대로 행 수가 아주 많지 않더라도 호출 빈도가 높거나 한 행의 크기가 크면 인덱스가 필요할 수 있다. 따라서 “몇 건 이상이면 인덱스를 만든다”는 고정 기준보다는 실제 실행 계획과 측정값을 사용해야 한다.

## 게시글 목록 예시

`article` 테이블이 다음 컬럼으로 구성되어 있다고 가정하자.

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | integer | 게시글 ID, 기본 키 |
| `category` | integer | 카테고리 ID |
| `writerId` | integer | 작성자 ID |
| `title` | varchar(255) | 제목 |
| `content` | CLOB/TEXT | 본문 |
| `regdt` | timestamp | 등록 시각 |

카테고리별 최신 게시글을 조회하는 쿼리는 다음과 같다.

```sql
SELECT id, category, writerId, title, content
FROM article
WHERE category = 10
ORDER BY id DESC
LIMIT 10 OFFSET 20;
```

### 사내 공지 서비스

매주 공지 한 건이 등록된다면 1년에 약 52건, 10년에 약 520건이 쌓인다. 직원 1,000명이 새 공지를 5분 안에 한 번씩 조회한다고 단순 가정하면 평균 요청률은 다음과 같다.

> `1,000회 ÷ 300초 ≈ 3.33 RPS`

기존 계산의 6.67 TPS가 아니라 3.33 RPS다. API 한 번이 게시글 목록과 상세 조회를 각각 호출하는 구조처럼 사용자 한 명당 DB 조회가 두 번이라면 DB 쿼리 기준으로 약 6.67 QPS가 될 수 있지만, 요청 수와 DB 쿼리 수를 구분해야 한다.

520건을 조회하는 서비스라면 `category` 인덱스가 없어도 목표 응답 시간을 만족할 가능성이 높다. 그러나 이 경우에도 실제 실행 빈도, 행 크기와 실행 계획을 확인해야 하며 “작은 테이블에는 인덱스가 절대 필요 없다”는 뜻은 아니다.

### 대형 커뮤니티

하루 5,000건씩 게시글이 등록되면 1,000만 건에 도달하는 데 약 5.5년이 걸린다. 이 테이블을 카테고리 조건으로 반복해서 풀 스캔하면 DB CPU와 I/O가 포화될 수 있다.

조회 패턴이 `category = ? ORDER BY id DESC`라면 단일 `category` 인덱스보다 필터와 정렬을 함께 고려한 복합 인덱스가 더 적합할 수 있다.

```sql
CREATE INDEX idx_article_category_id
    ON article (category, id DESC);
```

작성자별 최신 글 조회도 자주 사용한다면 별도의 조회 패턴이다.

```sql
SELECT id, category, writerId, title
FROM article
WHERE writerId = 10
ORDER BY id DESC
LIMIT 10 OFFSET 10;
```

```sql
CREATE INDEX idx_article_writer_id
    ON article (writerId, id DESC);
```

인덱스의 정렬 방향 지원과 실제 사용 여부는 DBMS 및 버전에 따라 다르므로 `EXPLAIN`으로 확인한다. 목록에서 본문 `content`가 필요하지 않다면 제외하는 것도 읽기 I/O와 응답 크기를 줄이는 데 도움이 된다.

## 문자열 검색과 전문 검색

일반적인 B-tree 인덱스는 다음과 같은 접두사 검색에는 사용될 가능성이 있다.

```sql
WHERE title LIKE 'database%'
```

반면 문자열 중간을 찾는 다음 조건은 일반적인 B-tree 인덱스를 활용하기 어렵다.

```sql
WHERE title LIKE '%database%'
```

대량 데이터에서 중간 단어 검색이 필요하다면 MySQL `FULLTEXT`, Oracle Text, PostgreSQL 전문 검색처럼 DBMS가 제공하는 전문 검색 기능이나 Elasticsearch/OpenSearch 같은 검색 엔진을 검토한다. 언어별 형태소 분석, 검색 정확도, 동기화 지연과 운영 비용까지 고려해 선택해야 한다.

## 활동 로그 예시

`activityLog` 테이블이 다음 컬럼으로 구성되어 있다고 가정하자.

| 컬럼 | 타입 |
| --- | --- |
| `id` | integer |
| `userId` | integer |
| `activityType` | varchar(20) |
| `activityDate` | date |
| `activityDatetime` | timestamp |
| `memo` | varchar(200) |

일평균 방문 회원이 10만 명이고 한 명당 평균 다섯 번 활동한다면 하루 50만 건, 30일 기준 약 1,500만 건이 쌓인다.

사용자의 특정 날짜 활동을 최신순으로 조회한다고 하자.

```sql
SELECT id, userId, activityType, activityDate, activityDatetime, memo
FROM activityLog
WHERE userId = 123
  AND activityDate = DATE '2024-07-31'
ORDER BY activityDatetime DESC;
```

이 조회가 빈번하고 사용자별 활동도 많다면 다음과 같이 필터와 정렬을 함께 만족하는 복합 인덱스를 우선 검토할 수 있다.

```sql
CREATE INDEX idx_activity_user_date_datetime
    ON activityLog (userId, activityDate, activityDatetime DESC);
```

사용자 한 명의 전체 데이터가 충분히 적다면 `(userId)` 단일 인덱스로도 목표 성능을 만족할 수 있다. 어떤 구성이 좋은지는 사용자별 행 수의 분포, 쿼리 빈도와 실행 시간을 측정해서 결정한다.

날짜별 활동 통계 쿼리는 다른 조회 패턴이다.

```sql
SELECT activityDate, activityType, COUNT(*) AS activityCount
FROM activityLog
WHERE activityDate = DATE '2024-07-28'
GROUP BY activityDate, activityType;
```

이 쿼리를 자주 실행한다면 `(activityDate, activityType)` 복합 인덱스가 필터링과 그룹화에 도움을 주고, DBMS에 따라 커버링 인덱스로도 동작할 수 있다. 하루에 한 번만 실행하는 배치이고 운영 쿼리에 영향을 주지 않는다면 30초가 걸리더라도 허용할 수 있다. 반대로 데이터 증가로 배치가 서비스 트래픽과 경합하거나 완료 시간 목표를 넘기기 시작하면 인덱스, 사전 집계 테이블, 파티셔닝 또는 분석용 저장소를 검토한다.

## 선택도는 중요한 기준이지만 절대 규칙은 아니다

선택도는 조건으로 얼마나 적은 행을 골라낼 수 있는지를 나타낸다. 실무에서는 대략 다음과 같이 생각할 수 있다.

> `선택도 = 서로 다른 값의 수 ÷ 전체 행 수`

회원 100만 명의 `gender` 값이 `M`, `F`, `N` 세 종류이고 `F`가 50만 건이라면, `gender = 'F'`는 전체의 절반을 읽으므로 단독 인덱스의 효과가 작을 수 있다.

```sql
SELECT *
FROM member
WHERE gender = 'F'
  AND birthYear = 1990;
```

이 쿼리가 중요하다면 `gender`만 볼 것이 아니라 `(gender, birthYear)` 또는 `(birthYear, gender)` 중 실제 데이터 분포와 다른 조회 패턴에 맞는 구성을 실행 계획으로 비교해야 한다. 통계 정보와 값의 치우침에 따라 옵티마이저가 인덱스를 사용하지 않을 수도 있다.

낮은 선택도의 컬럼도 특정 값만 매우 적게 존재하고 그 값을 자주 찾는다면 좋은 인덱스 후보가 될 수 있다. 작업 큐가 대표적인 예다.

```sql
CREATE TABLE jobQueue (
    jobId varchar(16) PRIMARY KEY,
    status char(1) NOT NULL
);
```

대부분의 작업이 완료 상태 `C`이고 대기 상태 `W`는 소수라면 다음 조회는 자주 실행되면서도 매우 적은 행만 찾는다.

```sql
SELECT jobId
FROM jobQueue
WHERE status = 'W'
ORDER BY jobId
LIMIT 100;
```

이 경우 `(status, jobId)` 인덱스가 유용할 수 있다. PostgreSQL처럼 부분 인덱스를 지원하는 DBMS라면 `WHERE status = 'W'`인 행만 인덱싱하는 방법도 있다. 여러 실행기가 동시에 작업을 가져간다면 인덱스와 별개로 중복 처리 방지를 위한 잠금, lease 또는 `FOR UPDATE SKIP LOCKED` 같은 동시성 제어가 필요하다.

## 복합 인덱스의 컬럼 순서

복합 인덱스는 단순히 조건절에 나온 컬럼을 모두 넣는 기능이 아니다. 일반적인 B-tree에서는 선두 컬럼부터 사용할 수 있는 조건이 중요하다.

```text
(userId, activityDate, activityDatetime)
 └─ equality ─┘ └─ equality ─┘ └─ range·order ─┘
```

보통 다음 순서로 검토한다.

1. 자주 사용하는 equality 조건
2. 범위를 크게 줄이는 조건
3. range 조건과 정렬 컬럼
4. 조회 결과만 전달하기 위한 포함 컬럼

하지만 무조건 “선택도가 높은 컬럼을 앞에 둔다”는 규칙도 정확하지 않다. 실제 쿼리가 인덱스의 선두 컬럼을 사용하는지, 한 인덱스로 필터와 정렬을 얼마나 해결하는지가 더 중요하다.

## 커버링 인덱스

커버링 인덱스는 쿼리에 필요한 컬럼을 모두 포함해 테이블의 본문 행 접근을 줄일 수 있는 인덱스다.

```sql
SELECT activityDate, activityType
FROM activityLog
WHERE activityDate = DATE '2024-07-31'
  AND activityType = 'VISIT';
```

`(activityDate, activityType)` 인덱스가 있다면 이 쿼리는 index-only scan의 후보가 된다. 반면 `SELECT *`는 인덱스에 없는 `memo` 등의 값을 얻기 위해 테이블 행에 접근해야 한다.

다만 “필요한 컬럼이 인덱스에 있으면 실제 데이터에 절대 접근하지 않는다”고 단정할 수는 없다. PostgreSQL은 행의 가시성 확인을 위해 heap에 접근할 수 있고, DBMS·스토리지 엔진과 트랜잭션 상태에 따라 실제 동작이 달라진다. 실행 계획과 실제 buffer read를 확인해야 한다.

## 인덱스도 비용이 든다

인덱스는 조회를 빠르게 할 수 있지만 공짜가 아니다.

- `INSERT`, `UPDATE`, `DELETE` 때 관련 인덱스도 변경해야 한다.
- 인덱스가 늘어나면 디스크와 buffer pool 사용량이 증가한다.
- 비슷하거나 중복된 인덱스는 쓰기 비용만 늘릴 수 있다.
- 넓은 커버링 인덱스는 읽기 이점보다 저장·갱신 비용이 커질 수 있다.
- 인덱스가 많으면 옵티마이저가 실행 계획을 고르는 비용도 증가한다.

새 인덱스를 추가하기 전에 다음을 확인한다.

1. 기존 인덱스의 선두 컬럼 조합으로 같은 효과를 낼 수 있는가?
2. 새 쿼리의 요구사항이나 정렬 조건을 조금 바꿀 수 있는가?
3. 실제 `EXPLAIN`에서 새 인덱스를 사용하는가?
4. 읽기 개선량이 쓰기·저장 비용보다 큰가?
5. 인덱스를 만든 목적과 대상 쿼리를 기록했는가?

운영 환경과 비슷한 데이터 분포에서 `EXPLAIN ANALYZE`를 사용할 때는 실제 쿼리를 실행한다는 점을 기억하고, 무거운 변경 쿼리나 운영 DB에서는 특히 주의한다.
