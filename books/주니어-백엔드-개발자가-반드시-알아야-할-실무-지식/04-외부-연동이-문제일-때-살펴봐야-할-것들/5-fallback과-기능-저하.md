# Fallback과 기능 저하

> [외부 연동이 문제일 때 살펴봐야 할 것들](./README.md)

> [!NOTE]
> **Fallback의 허용 범위는 기능의 위험에 따라 달라집니다**
>
> 부가 정보는 오래된 값이나 생략으로 대체할 수 있지만 결제·권한처럼 안전이 중요한 기능은 실패를 명확히 드러내야 합니다.

## 빠른 복습

- Fallback은 오류를 숨기는 것이 아니라 핵심 기능을 유지하도록 품질을 의도적으로 낮추는 전략이다.
- 추천·부가 정보는 stale cache나 생략이 가능하지만 결제·권한 검사는 fail-closed가 안전할 수 있다.
- 대체 데이터의 최대 age, 사용자 안내와 fallback 자체의 실패를 함께 정의한다.

빠르게 실패시키더라도 사용자에게 항상 오류 화면만 보여줘야 하는 것은 아니다. 데이터 특성에 따라 다음 fallback을 사용할 수 있다.

- 추천 API 장애 시 인기 상품 목록 표시
- 배송비 API 장애 시 “계산 중” 상태로 주문 단계 제한
- 외부 프로필 조회 실패 시 마지막으로 저장한 stale cache 사용
- 알림 전송을 durable queue에 저장하고 비동기 재처리
- 로그 수집 실패 시 핵심 요청과 분리하고 제한된 local buffer 사용

결제 승인이나 권한 검사처럼 오래된 값으로 대체하면 위험한 기능은 fail-closed가 적절할 수 있다. 반면 추천·부가 정보는 기능을 생략하는 graceful degradation이 더 나을 수 있다. fallback 데이터의 최대 허용 age와 사용자 안내를 명시한다.

Stale cache를 fallback으로 사용할 때 필요한 TTL, stampede와 무효화 전략은 [서버 캐시](../02-느려진-서비스-어디부터-봐야-할까/2-서버-성능-개선-기초.md#서버-캐시)를 참고한다.
