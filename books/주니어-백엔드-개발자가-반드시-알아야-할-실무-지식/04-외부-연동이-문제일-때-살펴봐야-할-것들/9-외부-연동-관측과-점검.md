# 외부 연동 관측

> [외부 연동이 문제일 때 살펴봐야 할 것들](./README.md)

> [!IMPORTANT]
> **Dependency별 지연과 보호 장치 상태를 나눠 보세요**
>
> 평균뿐 아니라 p95·p99, 단계별 Timeout, retry, bulkhead 거절과 circuit 상태를 같은 시점에 관측해야 원인을 좁힐 수 있습니다.

## 빠른 복습

- 전체 API latency만 보지 말고 dependency·operation별 pool, connect, TTFB와 전체 call 시간을 나눈다.
- 평균보다 p95·p99, timeout, retry, bulkhead 거절과 circuit 상태를 관측한다.
- 공급자 request ID, trace ID와 idempotency key를 연결해 양쪽 로그를 대조한다.
- 장애 주입 테스트로 무응답·느린 body·중복 webhook과 공급자 장애 복구를 검증한다.
- TPS Lab 결과 읽기에서 성공률, tail latency, thread·queue와 retry 호출 증폭을 같은 결과로 비교한다.

외부 연동은 “전체 API가 느리다”는 지표만으로 원인을 찾기 어렵다. dependency·operation별로 다음을 측정한다.

- 호출 수와 성공·오류 status 분포
- pool 대기, DNS, connect, TLS, TTFB와 전체 call latency
- p50·p95·p99와 timeout 수
- retry attempt 수, retry 성공률과 추가 호출량
- bulkhead 동시 사용량·대기·거절 수
- rate-limit 대기와 `429`·`Retry-After`
- circuit 상태, 전환과 차단 호출 수
- HTTP pool leased·available·pending connection
- fallback 사용량과 stale data age
- 공급자 request ID, 우리 trace ID와 idempotency key

우리 trace에서 downstream 구간을 별도 span으로 남기고 민감 정보를 제거한 request ID를 로그에 기록하면 공급자와 장애 시점을 대조하기 쉽다. SLO와 alert도 평균 latency보다 tail latency, 오류율, pool 포화와 circuit 상태를 중심으로 설정한다.

전체 API trace에서 DB·외부 API 중 병목 후보를 고르는 방법은 [먼저 병목을 찾는다](../02-느려진-서비스-어디부터-봐야-할까/2-서버-성능-개선-기초.md#먼저-병목을-찾는다), p95·p99의 의미는 [응답 시간](../02-느려진-서비스-어디부터-봐야-할까/1-처리량과-응답-시간.md#응답-시간)을 참고한다.

## 외부 연동 점검 순서

1. 어떤 사용자 기능이 어떤 dependency를 반드시 거치는지 지도를 만든다.
2. 각 연동의 계약 quota, rate limit과 정상 latency 분포를 확인한다.
3. pool·connect·read·call timeout의 실제 범위를 검증한다.
4. 상태 변경 API가 idempotent하고 결과 확인 수단이 있는지 확인한다.
5. retry 대상, 최대 횟수, backoff·jitter와 전체 budget을 정한다.
6. dependency별 bulkhead, bounded queue와 rate limit을 부하 테스트한다.
7. circuit의 실패·slow call 기준, 최소 표본과 half-open probe를 검증한다.
8. fallback과 fail-open·fail-closed 정책을 제품 담당자와 정한다.
9. DB transaction이 외부 호출 동안 열려 있지 않은지 확인한다.
10. HTTP/1.1·HTTP/2에 맞는 pool과 connection 반환을 확인한다.
11. timeout·응답 유실·중복 webhook·공급자 장애를 주입해 복구를 시험한다.
12. 핵심 연동은 이중화의 비용과 실제 failure domain을 검토한다.

## 핵심 정리

- 전체 요청의 성능과 가용성은 필수 dependency 중 가장 느리고 불안정한 구간의 영향을 받는다.
- timeout은 pool, connect, read와 전체 call deadline을 구분하고 상위 요청의 시간 budget 안에 맞춘다.
- 결제 timeout은 실패가 아니라 결과 불명일 수 있으므로 멱등성, 상태 조회와 대사가 필요하다.
- retry는 안전한 요청에만 적은 횟수로 적용하고 backoff, jitter와 전체 retry budget을 둔다.
- rate limit은 요청 시작률을, bulkhead는 동시 실행 수를 제한하며 둘은 목적이 다르다.
- circuit breaker는 동시성을 제한하지 않으므로 bulkhead와 함께 사용한다.
- fallback은 데이터의 신선도와 위험에 따라 fail-open·fail-closed를 구분한다.
- 외부 호출 동안 DB transaction을 오래 유지하면 DB connection pool까지 함께 포화될 수 있다.
- HTTP pool 크기는 downstream 용량과 HTTP protocol의 multiplexing 특성을 고려해 정한다.
- 공급자 이중화는 API 전환뿐 아니라 중복 처리, 데이터, 정산과 운영 절차까지 포함한다.
- dependency별 latency 단계, retry, pool, bulkhead와 circuit 상태를 관측해야 장애 원인을 찾을 수 있다.
