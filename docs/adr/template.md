# ADR-NNNN: 결정 제목

이 전체 양식은 언어·플랫폼·데이터 저장 방식처럼 되돌리기 비싼 결정에 사용한다.
국소적이고 쉽게 되돌릴 수 있는 결정은 `배경과 문제 정의`, `결정 기준`, `검토한 선택지`,
`결정`, `결과와 영향`만 남기는 짧은 형식을 사용해도 된다. 문서 분량보다 판단 근거와 증거가 중요하다.

- 상태: Proposed | Accepted | Rejected | Superseded | Deprecated
- 작성일: YYYY-MM-DD
- 결정자: 이름 또는 역할
- 상위 기획 문서: Product Brief, PRD 또는 Product Spec 링크
- 관련 ADR: ADR-NNNN
- 대체한 ADR: 없음
- 대체된 ADR: 없음
- 검토 예정일: YYYY-MM-DD 또는 검토 조건

## 한 문장 결정

> `<문제와 제약>`의 상황에서 `<원하는 품질>`을 얻기 위해 `<선택지>`를 선택하고
> `<다른 선택지>`를 채택하지 않는다. 그 대가로 `<감수하는 비용>`을 받아들인다.

## 배경과 문제 정의

결정이 필요한 실제 문제를 기술한다.

- 누가 어떤 상황에서 영향을 받는가?
- 지금 무엇이 어렵거나 위험한가?
- 결정하지 않으면 어떤 비용이나 위험이 생기는가?
- 이 결정이 해결하지 않는 문제는 무엇인가?

기술 이름으로 시작하지 않는다. `Kotlin을 사용할 것인가?`보다
`업무 상태를 안전하게 표현하면서 장기간 운영할 서버 언어를 무엇으로 할 것인가?`처럼 쓴다.

## 상위 제품 근거

기술 결정이 보호하려는 사용자 시나리오와 결과를 상위 기획 문서에서 가져온다.
아직 기획 문서가 없다면 사실처럼 만들지 않고 `미작성` 또는 `가설`로 표시하며,
ADR은 `Proposed` 상태로 유지한다.

| 항목 | 내용 | 상위 문서 근거 |
| --- | --- | --- |
| 타깃 오디언스 |  | Product Brief |
| 북극성 시나리오 |  | Product Brief |
| 첫 마일스톤의 사용자 결과 |  | PRD |
| 관련 기능 요구사항 |  | FR/UC ID |
| 관련 비기능 요구사항 |  | NFR ID |

지연 시간, 가용성, 일관성, 처리량 같은 품질 속성은 기술 자체의 목표로 두지 않고
사용자가 과업을 완료하는 데 어떤 영향을 주는지 설명한다.

- 선택지 A
- 선택지 B
- 선택지 C

후보를 형식적으로만 나열하지 않는다. 실제로 채택할 수 있었던 선택지만 포함한다.

## 근거 비교

공식 문서에서 확인되는 사실과 그 사실이 프로젝트에 주는 의미를 분리한다.

| 결정 기준 | 선택지 | 확인된 사실 | 프로젝트에 대한 해석 | 출처 |
| --- | --- | --- | --- | --- |
|  |  | 공식 문서의 사실 | 사실로부터 도출한 판단 | 링크 |

점수를 합산해 답을 자동으로 만들지 않는다. 치명적인 기준을 충족하지 못하는지,
어떤 장점을 얻는 대신 어떤 비용을 지불하는지를 드러내는 데 사용한다.

## 선택지별 트레이드오프

### 선택지 A

#### 얻는 것

- 장점과 그 장점이 유효한 조건

#### 치르는 비용과 위험

- 단점, 운영 책임, 학습 비용

#### 이 선택지가 더 적합해지는 조건

- 프로젝트 요구가 어떻게 바뀌면 이 선택지가 더 나아지는가?

## 결정

선택한 선택지와 이유를 기술한다.

`널리 사용된다`, `성능이 좋다`, `익숙하다`만으로 결론 내리지 않는다.
상위 결정 기준을 어떻게 충족하고 어떤 비용을 받아들이는지 함께 쓴다.

## 결과와 영향

### 긍정적 결과

- 기대하는 효과

### 부정적 결과와 감수한 비용

- 복잡도, 제약, 새로 생기는 운영 책임

### 중립적 결과

- 좋고 나쁨보다 후속 결정을 강제하는 변화

- 새로 배운 점:
- 유지, 수정 또는 대체 결정:

## 외부 검토자가 확인할 수 있는 논리

ADR은 이력서 문서가 아니다. 다만 구현과 운영의 증거를 함께 남기면 나중에 경험을 설명할 때
결론만 포장하지 않고 실제 의사결정 과정을 재구성할 수 있다.

| 검토자가 알고 싶은 것 | 이 ADR에서 답하는 위치 |
| --- | --- |
| 어떤 문제가 있었는가? | 배경과 문제 정의 |
| 어떤 제약 속에서 결정했는가? | 범위와 비범위, 제약과 전제 |
| 무엇을 중요하게 보았는가? | 우선순위가 있는 결정 기준 |
| 어떤 대안을 실제로 검토했는가? | 검토한 선택지, 근거 비교 |
| 왜 이 방안을 골랐고 무엇을 포기했는가? | 선택지별 트레이드오프, 결정, 결과와 영향 |
| 위험을 어떻게 통제했는가? | 위험 완화책 |
| 실제로 적용하고 확인했는가? | 검증 계획과 성공 기준, 후속 작업 |
| 결과와 실패에서 무엇을 배웠는가? | Outcome review |

작성 시 다음 원칙을 지킨다.

- 구현 전에는 기대 효과를 성과처럼 쓰지 않는다. 가설, 실험, 성공 기준으로 쓴다.
- 구현 후에는 가능하면 PR, 테스트, 장애 기록, 지표처럼 다시 확인할 수 있는 증거를 연결한다.
- 실패한 시도와 버린 대안도 당시의 근거와 배운 점이 있으면 남긴다.
