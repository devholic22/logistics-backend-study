# 기획 문서 작성 체계

이 디렉터리의 문서는 기능 목록보다 사용자 시나리오를 먼저 작성한다.
목적은 그럴듯한 해결책을 설명하는 것이 아니라, 아직 만들지 않은 제품을 이야기로 시뮬레이션하여
누구의 어떤 문제를 풀지, 무엇을 만들지, 어떻게 검증할지를 단계적으로 좁히는 것이다.

## 문서 흐름

| 문서 | 답할 질문 | 포함할 내용 | 포함하지 않을 내용 |
| --- | --- | --- | --- |
| Product Brief | 왜 만드는가? | 테제·안티테제, 타깃, 현재 경험, 북극성 시나리오, 목표 지표 | 상세 API, DB schema, framework 선택 |
| PRD | 무엇을 먼저 만드는가? | 유스 케이스, 첫 마일스톤, 우선순위, 기능·비기능 요구사항, 검증 계획 | 구현 클래스, 상세 transaction 방식 |
| Product Spec | 어떻게 동작하게 만드는가? | 사용자 흐름, 상태와 경계, 실패·복구, 관측·출시 계획, ADR 연결 | 상위 문제를 근거 없이 다시 정의하는 일 |
| ADR | 왜 이 기술 방안을 선택하는가? | 결정 기준, 대안, 근거, 결과와 재검토 조건 | 사용자 문제와 무관한 기술 선호 |

흐름은 한 방향으로 끝나지 않는다.

```text
Product Brief → PRD → Product Spec → 구현·운영
       ↑          ↑          ↑            │
       └──────────┴──────────┴── 새로 배운 사실
```

뒤 단계에서 시나리오의 빈틈이나 잘못된 가정을 발견하면 앞 문서를 수정한다.
문서를 고정된 계약으로 취급해 새 정보를 무시하지 않는다.

## 핵심 판단 규칙

### 시나리오가 출발점이다

시나리오는 `캐릭터(페르소나 + 그 순간의 동기) + 시뮬레이션`으로 작성한다.
시뮬레이션은 기능이 보이는 장면만 쓰지 않고 사용자가 문제를 인식한 순간부터 결과를 확인할 때까지 이어간다.
정상 흐름 사이의 생략된 단계, 실패, 복구와 오용 가능성도 찾는다.

### 테제에는 안티테제가 따른다

성공할 이유만 적지 않는다. 사용자가 필요로 하지 않거나 기존 방식이 충분해서 제품이 가치 없을 수 있는 이유를
같이 적는다. 검증은 테제를 증명하는 활동이 아니라 안티테제를 반증하거나 받아들이는 활동이다.

### 첫 마일스톤은 완결된 가치다

우선순위는 기능 수가 아니라 `사용자 가치 × 영향을 받는 규모 × 지속 시간`과 전체 비용을 함께 본다.
전체 비용에는 구현뿐 아니라 예외 처리, 테스트, 문서, 운영, 지원과 만들지 않았을 때 생기는 비용도 포함한다.
첫 마일스톤은 여러 시나리오의 앞부분을 조금씩 만드는 대신 좁은 오디언스의 이야기 하나를 끝까지 완성한다.

### 비기능 요구사항도 사용자 언어로 쓴다

지연 시간, 가용성, 처리량, 데이터 일관성과 확장성은 독립적인 기술 목표가 아니다.
어떤 사용자가 어떤 과업을 수행할 때 어느 정도의 실패나 지연을 경험하는지로 표현하고,
측정하기 쉬운 시스템 지표만 최적화하지 않는다.

## 문서 상태 게이트

| 상태 | 의미 |
| --- | --- |
| Draft | 탐색 중이다. 미확인 가정과 빈 항목이 있을 수 있다. |
| Proposed | 필수 항목을 작성했고 검토할 수 있다. 구현 승인을 뜻하지 않는다. |
| Accepted | 완료 조건을 통과했고 첫 마일스톤 구현의 기준으로 사용한다. |
| Validating | 도그푸딩, 테스트 또는 운영 지표로 가설을 확인 중이다. |
| Superseded | 새 정보로 대체됐다. 과거 판단을 지우지 않고 대체 문서를 연결한다. |

`Accepted` 전에는 [루트 작업 지침](../../AGENTS.md)의 완료 조건을 확인한다.
